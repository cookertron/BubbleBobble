## 0. THE FOUR THINGS THAT CHANGE THE PLAN

Read these before anything else; each one invalidates something the project believed.

### 0.1 There is NO attract mode and NO demo

The docs call `$8CC7` "the attract entry".  `$8CC7` is `CALL $95F3` — the one-shot
cold-start setup.  There is no demo anywhere.

Driven for **16,749 frames (335 seconds of machine time)** with no keys pressed and 24
candidate exit addresses watched: not one fires.  `$8D25` (the main-loop chain) is never
entered, the entity table `$FD80..$FDF7` never changes a byte, the round counter stays 0.
The front end runs **no round painter, no scroll and no in-play pass** — not one PC in
`$4000..$7FFF` over the whole run from `$8CC3` to the wait loop.

The title screen's wait loop has **no counter, no timer, no fall-through and exactly two
exits**: `'1'` starts one player, `'2'` starts two, one credit either way.  Measured
200,000 iterations with no key, and with 3/4/5 held, and it never leaves.

*Consequence:* a whole sub-system the plan budgeted for does not exist.  No synthetic
input source, no recorded input stream, no PRNG census extension.  All four PRNG / `LD A,R`
sites the front end reaches — `$971D`, `$9775`, `$9715`, `$FEAC` — are **already** in the
port's censuses, so `BB_Rng` will not throw.

### 0.2 There are TWO front ends, and the port already owns half of one

| | |
|---|---|
| **The cold-start front end** | `$F5BC..$8CD9`.  Two control-select menus (`$F5E7` called twice, once per player, unconditionally), the `$FAC3` 48K/128K probe, `$95F3`'s whole cold-start init, IM 2 arming, the `$E000->$5B00` relocation.  Runs **ONCE per load**. |
| **The per-game front end** | The **TAIL of `$96DF`** — the very routine the port already models as `gameReset()`.  `$96DF..$970D` is the reset, `$970E EI`, and `$970F..$97E9` is the title screen, the sparkle loop and the "1 OR 2 TO PLAY" key wait. |

**The cold-start front end is then PHYSICALLY DESTROYED.**  `$F5BC..$F9FF` sits inside the
game's bitmap shadow `$E000..$F7FF` and colour shadow `$F800..$FAFF`: measured **1,050 of
1,092 bytes gone after 120 frames of play**.  It cannot be re-entered because it no longer
exists.

*Consequence:* the title screen attaches to a method the port **already has**, and the
control select is a separate, once-per-load object that must be modelled as such.  The
exit direction does not re-enter `$8CC3` or `$F5CC`: the main loop RETs to `$8CDC` through
the word `$8D05 PUSH HL` left on the stack, the banner counts `$FEC9` to the eight-bit
wrap, and it **falls through** into `$8D02`, which re-pushes `$8CDC` and CALLs `$96DF`
again.  `$8CC4 LD SP,$96DD` sets a stack ceiling, and only already-executed cold-start
code is destroyed, so **`$96DF` is a clean CALL/RET pair and the port CAN model the title
screen as a function call.**

> **CORRECTED 2026-09-26 (M7.39b): the floor was given as `$96B1`, 44 bytes.  Both halves
> are wrong** — measured 42 bytes with interrupts ON and 20 with them OFF.  And the deeper
> point the correction exposes: **the stack addresses are ENTRY-DEPENDENT.**  Entered
> naturally from `$8D02`/`$8D06`, SP is `$96D9` and pushes land at `$96D7`; entered bare at

### 0.3 The `$F5D2` contradiction: settled three ways, and SPEC was right

`$F5D2..$F5E1` is a **16-byte key-table STAGING BUFFER**, written through a 16-bit cursor
at `$F5E5` (shipped pointing at `$F5D2`, advanced by 8 per player).  Its *tape content*
happens to be the easter-egg ASCII `"MUSIC BY TIM FOLLIN"`.

**Nothing ever prints it.**  `LD IX,$F5D2` (`DD 21 D2 F5`) occurs **zero times** in
`$4000..$FFFF`; `$802E` takes its string from IX; and the text is not NUL-terminated (the
first `$00` at or after `$F5D2` is at `$F61A`, 72 bytes on).  The word `$F5D2` occurs
exactly twice in the whole 64K — at `$F5CD` (the operand of `$F5CC LD HL,$F5D2`) and at
`$F5E5` (the cursor's init value).  `"LIN"` survives at `$F5E2..$F5E4` as a fossil.

Three states, measured across 14 captures plus both static images:

| state | captures |
|---|---|
| the credit string | tape, `boot`, `title` |
| the built key table `F7 10 EF 04 EF 01 EF 08 / 1F 02 1F 01 1F 08 1F 10` | `afterctrl`, `afterctrl48` |
| inert round-dependent leftovers | every in-play capture, and `image.bin` |

So **both doc statements were true at different moments** and neither was wrong; what was
missing was the word REUSE.  `docs/SPEC.md`'s `$95F3` claim — `LD DE,$B5FD / LD BC,$10 /
LDIR` from `HL=$F5D2`, table beginning `F7 10` — is **CORRECT**.  The one thing SPEC did
not say is that **HL is a live parameter**: there is no `LD HL,nn` anywhere in
`$95F3..$9602`; HL is threaded unchanged from `$F5CC` through two JPs and a CALL.  The
channel is the fact, not the address.

### `$995A`'s `OR $40` and `$9770`'s `BIT 6,(HL)` are ONE MECHANISM

Every attribute `$995A` writes is forced BRIGHT; the sparkle loop **skips every BRIGHT
cell**.  That is why the title text never shimmers.  A port that drops the `OR $40` makes
the title text flicker in random colours.

Measured: the five attribute values written are `$47 $46 $43 $CC $45` — every one has bit
6 set — and A on entry was `$07 $06 $03 $8C $05`, bit 6 **clear**, so the bright bit comes
only from the OR.  Rate check: 167 bright cells of 768 predicts a recolour rate of
`1/8 × (1 − 167/768)` = 9.79%; measured 1,461 writes in 14,979 iterations = **9.75%**.

### The two exits

Key `'1'` (bit 0) leaves at `$979E` = one player; key `'2'` (bit 1) at `$9790` = two
players; both in half-row `$F7`.  Keys 3/4/5 are read in the same `IN` and **ignored**.
Each branch DECs `$FED3` (the credit count) **once** and sets `$FD87` (P1 +7) and/or
`$FD91` (P2 +7) to `$80`.  **`'1'` beats `'2'`** when both are held.

Then `$97AB..$97C6`, the release wait: **the CLS re-runs inside the loop** until all forty
keys are up, and `playersInit()` is not reached while a key is down.

## 3. THE CONTROL SELECT

`$F5BC` calls `$F5E7` **twice**, A=`'1'` then A=`'2'`, unconditionally.  Each call:
clears the screen, waits for all keys released, paints a rainbow attribute file, prints
`LICENSED BY FIREBIRD SOFTWARE` through **the ROM's channel-2 printer at AT 21,0**, draws
seven double-height ROM-charset strings (`$F607`), then spins in `$F664` on `$F7B3` until
the key is `'1'..'4'` **and is not the option the other player already took**.

`$F680` stores `key − '1'` in `$F982` and branches four ways:

| option | routine | table source |
|---|---|---|
| KEYBOARD | `$F723` -> the five-prompt redefine screen | built |
| SINCLAIR | `$F6B8` | preset `"6790"` the **first** time, `"1245"` every later time |
| KEMPSTON | `$F692` | eight **RAW** bytes at `$F9F4`, builder skipped |
| CURSOR TYPE | `$F6D0` | preset `"5807"` |

All four arms end by writing eight `[half-row, mask]` bytes through the 16-bit cursor at
`$F5E5`.  **`$F982` is written once and read by nothing, anywhere.**

There is **no exit back to the title** and no way to re-enter: the only ways out are into
the redefine screen, into the next player's pass, and `$F5CF JP $7274` with `HL=$F5D2` and
`A=$30`.

### `$F7B3` does not wait for an interrupt

`$F7B8` is `RST $38` — an **explicit call into the ROM's MASK-INT body**.  The loop drives
the ROM keyboard scan itself, so the whole menu runs with the ISR suppressed and IFF=0 on
arrival.  *This is the single most useful fact for the LAST-K design:* the port does not
need a background interrupt handler maintaining `$5C08`; it needs the scan driven
**synchronously**, once per loop pass, which is a function the port can write and test.

> **CORRECTED M7.53 (the H-a review, measured).**  Only player 1's FIRST arrival at `$F7B3` has
> IFF 0.  The routine RST `$38` enters ends by re-enabling interrupts, so from the first key read on
> the menu runs with IFF 1: 98.7% of 377,800 steps over 50 idle frames, 50 frame interrupts accepted
> alongside 3,550 explicit calls, and player 2's paints take 5-6 interrupts each.  The scan IS driven
> synchronously once per pass -- AND by the frame interrupt.  H-b's LAST-K model must account for
> both (TRAPS #228).

### Redefine, `$F72F` / `$F6DB` / `$F988`

- `$F6DB` is a five-instruction lookup, `pair = table[ASCII − $30]`, with **no range check
  of its own**; the reader's accept filter is the only bound, and it matches the table
  exactly.
- **`$F988` is not a digit table.**  It is 96 bytes / 48 slots / **38 live entries**,
  covering every key of the 40-key matrix except CAPS SHIFT and SYMBOL SHIFT, with ENTER
  and SPACE reached by the reader substituting `']'` (`$5D`) and `'_'` (`$5F`).
- **`$F72F` reads FIVE keys** — four bindings plus the "ALL OK ?" answer — and stores the
  **third and fourth swapped**.
- The `R` answer, for **player 2 only**, arms an undocumented checksum cheat.
- **Two keyboard redefines in one session are IMPOSSIBLE**: `$F670`'s CP immediate is
  patched after the first.  Enumerated 4×4 by natural drives.
- 2P key clash: the "no check" claim is confirmed — the builder converts sequentially with
  no cross-player or per-key distinctness test, so both players may share a key.  The only
  runtime handling is LEFT-priority at `$AC15..$AC22`.

## 4. `$FAC3`, THE 48K/128K PROBE

27 instructions, **one caller** (`$F5C9`), four instructions into `$F5BC`, after both
control selects.  It syncs on a HALT, zeroes ROM FRAMES (`$5C78..$5C7A`), then counts
256-iteration blocks of a **contended** `CP (HL)` read of FRAMES' low byte until 255 ROM
ISR ticks have passed.  It accepts exactly `BC=$075E` or `$0763` -> `A=$30` (48K);
anything else loads `A=$80` and takes a `PUSH HL / RET` trampoline (`$FA3B -> $FA67`) that
**also returns to `$F5CC`**.

**No port access and no BANKM read — M6's "timing probe, not a BANKM read" holds.**

Measured with contention on: released keys give `$075E / $30 / 48K` on both the armed and
the naturally-driven path; every single key held gives `$0754..$0757` (or `$075D` for CAPS
alone) and **128K**; a Kempston direction gives `$075E` (the ROM ISR reads only `$FE`);
uncontended gives `$07AB`, exactly as documented.

The released-keys precondition **is not luck — it is enforced** by two identical
spin-until-all-keys-released gates, `$F5F0` (top of each `$F5E7`) and `$F7F9` (the sole
exit path of `$F7B3`).  A key held at the probe's first instruction is unreachable.  The
reachable fault is **17–24 frames of cumulative key-down inside the 255-frame (5.1 s)
black-screen window**, and the threshold is phase-invariant and key-dependent.

**The flag is stored NOWHERE.**  It is parked in `A'` at `$95F4`, read twice (`$9696 CP
$80`, `$96B0 CP $C9`) and consumed into three RET patches at `$8DC4` / `$8E05` / `$8E0A`,
which are the **only durable record** and which 17 call sites later execute.

## 5. THE FOUR BLOCKERS THE CRITIC CAUGHT IN THE READS

Each was a load-bearing claim that reached a reader's PORT ACTIONS wrong.  Listed because
"the agents agreed" is not the same as "the agents were right".

1. **The starfield attribute is not `$05`** — it is `$00..$07`, 128 each (§2).  Refuted by
   the reader's own verifier, again independently by another sub-block, and measured a
   third time by the critic; but the wrong number was still in the PORT ACTION and only
   the right one was in the finding.  This was the most likely way the next increment went
   wrong.
2. **The glyph requirement had five answers and none was the number.**  Measured: the
   **whole front end needs 57 distinct codes**, the port has **32**, **26 are missing**
   (`. : ? B J K Q X Z ] _` and the fifteen lowercase `a e f g i k l m n o r s t w y`).
   Title screen alone: 36 needed, 17 missing.
3. **`$97EB` clears 6,912 bytes to `$5AFF`**, not 6,911 to `$5AFE`.  Load-bearing because
   `$5AFF` is the credit line's ninth attribute cell and `test/bb.test.js:20309` already
   asserts `ram[0x5AFF] === (0x05 | 0x40)`.
4. **The high score is BOTH 20,000 and 200,000.**  Stored `$FFE1..$FFE4 = 00 00 02 00`
   (20,000 internal); rendered as **nine** digits `000200000` (200,000 displayed), because
   `$85F1` is a fixed template `'0'` that the digit builder never writes.  The port needs
   both numbers or a persistence layer and a gate will disagree forever.  Side facts:
   `afterctrl48`'s HUD buffer still reads `"  1000000"` — the tape's initial content — so
   **the title screen never shows a high score**; and `boss` holds `$FFE1..$FFE4 = 84 55
   04 00` while its HUD buffer still reads `"000200000"`, so the buffer is not repainted
   every frame.

## 6. THE DECLARED DEPARTURES — ONE DESIGN, NOT SEVEN

The reads produced **seven local workarounds**.  This is the single design, stated once.

1. **ONE glyph table, keyed by ROM character code, 57 entries**, drawn by
   `tools/make_banner.py` with its "no two inked glyphs share eight bytes" assert kept.
   `BB_BANNER_FONT` already *is* that table keyed by code — the port removed a
   position-indexed second font for exactly this reason (`web/game.js:836` says so).
   **Extend it; do not add a second one.**
2. **THREE printers over that one table, each a named method.**  Nobody had written down
   that there are three:
   - the in-game `$802E` walk — NUL-terminated, `LD BC,$3C00` hard-coded (the port has
     this: `bannerPrint` / `bannerCellSingle` / `bannerCellDouble`);
   - the front-end `$F863` / `$F887` walk — **`$40`-terminated**, charset base from the
     **CHARS sysvar `$5C36`**, row-doubled differently, with a self-patched enable byte at
     `$F850` and its own cursor pair `$F97D` / `$F97F`;
   - the Firebird line — **ROM channel 2 + `RST $10`**, single height.

     > **CORRECTED 2026-09-26 (M7.39b).**  This said "INK 8 / PAPER 8, which means *leave
     > the attribute alone*".  **Both readings were wrong**, and so was the counter-claim
     > from a phase's own output that it "writes `$0F` to all 32 cells".  SETTLED by
     > poisoning row 21 with **32 distinct values** (`$C0 | col` — FLASH and BRIGHT set,
     > ink and paper varying) and driving `boot -> $FA71 -> $F602` with a write-watch:
     >
     > ```
     >   poison in  : C0 C1 C2 … DE DF
     >   came back  : 00 01 02 … 1E 1F

     >
     > **`new = old & $3F`.**  Ink and paper SURVIVE; BRIGHT and FLASH are forced OFF.
     > Pinned by four more uniform poisons: `$FF -> $3F` (so the mask is `$3F`, not `$7F`
     > or `$BF`), `$3F -> $3F`, `$00 -> $00`, `$40 -> $00`, `$80 -> $00`.  The ROM writes
     > **all 32 cells** of row 21, one per printable character including the three spaces,
     > from PC `$0C08`.

     > The `$0F` a phase reported was **the ROM writing back what `$F82A`'s rainbow had
     > already left there** — TRAPS #44 exactly, a world that already held the answer.  A
     > JS gate that does not model the mask is blind to this unless it replays a POISONED
     > row, and that is the sharpest of H3's gate holes.
     >
     > From the same drive: **288 writes = (8 display + 1 attribute) x 32**, display
     > `$50A0 + col + $100*row`, 256 distinct display cells, attributes `$5AA0..$5ABF`
     > exactly, SP at `$FA71` = `$61A3` with 16 stack bytes written (`$6193..$61A2`), and
     > 16 sysvar addresses outside the two files.  Nothing else in 64K.
   **The charset BASE is the departure's boundary**: one constant, three routes to it, and
   an assertion that all three resolve to the same table.
3. **ONE attribute painter with two entries**: `attrRun` = `$995A` (the port has it), plus

4. **ONE LAST-K model.**  Because `$F7B3` drives the ROM scan synchronously via `RST $38`
   (§3), this is a *function*, not a background service: the ROM's K-DECODE mapping as a
   constraint table of **40 keys × 4 shift states = 160 rows**, with `$F7B3`'s accept

## 9. ADDED 2026-09-26 (M7.39): THE STARFIELD'S MASK TABLE OVERLAPS A LIVE VARIABLE

The table `$FEB0` indexes is **eight bytes at `$FEBD..$FEC4`** — and `$FEBD + 7` is
**`$FEC4`, the odd-frame ISR pass gate**.  It is not a constant:

| | |
|---|---|
| slots 0..6 | `80 40 20 10 08 04 02` — seven single bits, covering bits 7..1 |
| slot 7 | **`$FEC4` itself.**  `$01` in the tape image; **`$00` by the time the starfield reads it**, because `$96EF` — in the same routine, thirty-five BYTES (fifteen instructions) earlier — zeroes it |

`$FEC4` has **twelve writing sites** — *corrected M7.41: the nine `LD ($FEC4),A` below, plus
`LD ($FEC4),HL` at `$8CDF` and `$96EF`, plus `$9610`'s `$AA49` fill* — (`$8912`, `$8996`, `$8E71`, `$9055`, `$90A3`, `$90B2`,
`$90BA`, `$94CD`, `$9884`), a reader at **`$8DA2`**, and an `LD HL,$FEC4` at `$9610`.
**The port already writes it in three places**, including `reset()`'s
`ram[0xFEC4] = 0x14` — the in-play value.

**Bit 0 is slot 7's unique signature**, because slots 0..6 cover bits 7..1 and nothing
else covers bit 0.  Driven from `$9712` over a cleared screen:

| `$FEC4` | screen bytes with bit 0 set |
|---|---|
| `$00` | **0** of 1,350 lit |
| `$01` | **92** of 1,442 |
| `$FF` | **92** of 1,442 |

So slot 7 really does reach the screen, and on the title screen it is **zero**.

> **TWO CORRECTIONS TO THIS SECTION, 2026-09-26 (M7.39b), both of my own claims.**
>
> **(a) "128 of the 1,024 dots draw nothing at all" is REFUTED.**  I inferred 128 from
> "one eighth of 1,024", which assumes the slot index is uniform.  It is not — it is

>
> **(b) the bit-0 discriminator does NOT work on a `reset()`-fresh world.**  `reset()`

## 10. ADDED 2026-09-26 (M7.39b): THE STARFIELD IS **EXACTLY** REPRODUCIBLE

The measuring agent concluded "gate the shape, not the cell set" — its own distinct
display-cell count varied 923..958 across runs.  **That is refuted.**  Two independent
agents reached the same answer: the 1,024 dots are a pure arithmetic function of **two
numbers** — the `$FE86/$FE87` PRNG state and the 7-bit `R` phase at `$9712` — and a
twelve-line model reproduces the machine **row for row**: 1,024 of 1,024 rows over fifteen
`(seed, phase)` pairs, zero mismatches.

The walk is **`+51 mod 128`, with `+53` after dots 255, 511 and 767**, read at a fixed
**`+35`** offset.  Cause, provable from the code rather than fitted: `DJNZ`-not-taken plus
`DEC C` plus `JR nz` is **two extra M1 fetches**, so the walk advances by the iteration's
M1 count and each inner-loop rollover costs `+2`.  Swept all 128x128 `(step, offset)`
pairs with the bumps: **exactly one, `(51, 35)`, reproduces the display file.**

### The port's `BB_Rng._synth` is wrong from dot 256 onward

It implements a **flat `+51`**.  Diffed row for row from the machine's own opening phase:
flat `+51` agrees on **256 of 1,024** dots and then never again; with the three `+53` bumps
it is 1,024 of 1,024.  **768 of the addresses are wrong in the port as it stands.**

Note carefully how that number was hidden: the census comment says "1,020 of the 1,023
steps agree", which is the *same measurement* read the other way.  **A phase error never
heals, because the walk is an accumulator** — three wrong steps out of 1,023 is three
quarters of the output wrong.  The two framings differ by everything (TRAPS #201).

**Consequence for the gate:** it can assert the **exact 1,024-cell set**, four digests and
the whole address sequence, which is enormously stronger than any histogram.  The only
irreproducible ingredient is the opening phase (0..127), which the port legitimately draws
from the declared substitute — so a reproducible gate must set `rng.walk` / `rng.walkArmed`
directly rather than going through `BB_Rng.arm()`.
