**(1) The round gate.** `$A9F0 CP $50 / RET nz` — the tick is inert on every round but 80, including 81. **MEASURED** (h.profile(600000) on boss.pkl: `$A9ED`:808, `$AA0E`:25).

**(2) The spawn arm.** Observable only from a world where `$A839 == 0` on round 80 — `build/bossspawn.pkl` is that world, and the spawn fires there at frame ~38 [MEASURED]. boss.pkl cannot show it (`$A839 = 9`). The old SPEC's own caveat ("not dynamically forced") is now closed.

**(3) `$A9FC` is NOT A GATE AND NOT A DIVIDER.** The recurrence is `n' := (T - n) & $FF` with `T = mem[$8DBD]` low byte. With T fixed this map is an **INVOLUTION**, so the operand sits in a 2-cycle whose two members **sum to T** and which carries no information about change. The Z test is `n == T`, which requires 0 to be in the orbit; once it is, `{0,T}` is **absorbing** while T holds, so the gate then skips **every other call** — the opposite of a divider. MEASURED on boss.pkl: orbit sampled at `$A9FF` over frames 380–392 = (192,200),(192,248),(192,200),(192,248)…; **13 latches in 900 frames**, all with `$AA00 == 0`, at passes 3735,3737,…,3751 (stride 2) and 4624,4626,4628,4630; **zero** latches in the first 300 frames of boss.pkl, one in 300 frames of bossspawn.pkl. Its only effect is to stretch three of the body intervals.

**(4) `$AA05` IS THE BOSS'S ONLY DIVIDER, AND IT COUNTS MAIN-LOOP PASSES.** MEASURED on boss.pkl over 900 frames: 8547 passes, 266 body fires, and the interval **in passes** was exactly 32 on 262 of 265 intervals; the three exceptions were 35, 36 and 38 — extra = 3+4+6 = **13**, exactly the 13 `$A9FC` latches. **CAUSAL separation from frames**: the same state with contention ON and OFF gives 2890 vs 2933 passes and 90 vs 91 fires in 300 frames, frame-interval mean 3.324 vs 3.277 (spread 3.06..4.49), while the **pass interval stayed 32 in every interval of both runs**. A frame-counting divider would hold the frame interval constant; it does not.

**Consequence the port must carry.** SPEC.md's "one tile-step per axis every ~3.33 frames … ≈2.4 px/frame" is a **derived quantity of this machine's instruction timing**: 32 ÷ 9.5 passes-per-frame. The main loop `$8D0C..$8D70` **has no frame wait** (MEASURED: 2890 passes / 300 frames = 9.633; 8547 / 900 = 9.497; bossspawn 2560/300). **A port that ties the boss to video frames cannot reproduce any of this cluster's cadence.** Every differential gate here must sample on **main-loop passes** (count entries to `$8D1E` or `$A9ED`), never on frames.

**The CP/SUB pair, exactly** (the idiom question, settled). Both forms write their own immediate back; the difference is what A holds at the write.
- `CP n` leaves A = the value **read**, so `$A82E` stores T and the gate is `T_k == T_{k-1}` — a genuine **edge detector**, passing once per change of T, i.e. once per frame. MEASURED: `$A824` passed `$A831` 299 times in 300 frames, 898 in 900 (0.997/frame).
- `SUB n` leaves A = the **difference**, giving the involution above.

**Which is the game's standard idiom: CP, 6 to 1.** A whole-image scan of `$5B00..$FFF0` for "an immediate at p+1 stored back by a `32` within 8 bytes" returns **35 sites**: 27 `LD A,n`, **six `CP n`** (`$867F`, `$91CF`, `$9E56`, `$A09D`, `$A193`, `$A82C`), one `ADD A,n` (`$A430`), and **exactly one `SUB n` — `$A9FF`**. All seven carry the same cold immediate `$2A`, which is why **`$2A` means "never initialised", not "a constant"** [MEASURED as a static census + the six live readings].

**The two frame counters are themselves SMOs.** `$8DB5 LD HL,nn / INC HL / LD ($8DB6),HL` and `$8DBC LD HL,nn / INC HL / LD ($8DBD),HL`. MEASURED on boss.pkl over 200 frames: each entered 200 times, each counter +200 — **exactly one per video frame**. By contrast `$FEC8` (`$8D1E LD HL,$FEC8 / INC (HL) / CALL z,$7FFC`) advanced 1954 times in those 200 frames: it is a **main-loop PASS counter**, and `$7FFC` fires every 256 passes (7 times in 200 frames), **not** every 256 frames.

## 6. THE DRAW `$A8C1` — 144 BYTES, NOT 128

Entered only from `$AA29` (72 entries in 240 frames on boss.pkl, all from `$AA29`) [MEASURED]. The interior `$A8DD..$A924`, which nobody had disassembled, is now modelled and the model is **BYTE-EXACT against the machine: 144 writes in order** on boss.pkl, bosshit.pkl, bosskilled.pkl, bossspawn.pkl plus eight built worlds at the right-hand edge [MEASURED].

**Head.** `IX = $FD00 + ((2*Y) & $FF)` where `Y = ($A839)`. The doubling is **8-bit** (`ADD A,A`, B forced 0), so `Y ≥ 128` folds the index back inside `$FD00..$FDFF` — **which is the entity array, not the row table**. `A' = 4` is the outer char-row count, carried across `EX AF,AF'`; A itself is clobbered by the inner loop.

**Outer loop `$A8D3`, four iterations.** Reload HL from the 16-bit table entry at IX, add the **16-bit** quantity `($A8DC<<8)|($A8DB)`, `EX DE,HL` so HL = source / DE = screen, run the inner loop, swap back so HL = the screen pointer (the attribute stage needs it) and DE = the advanced source, step IX by 2. MEASURED at X=29, Y=12: D walks `$48,$4A,$4C,$4E,$50,$52,$54,$56,$58` with E parked at `$FD`, and the derived attribute row ends at `$5A00` instead of `$5900`. **UNREACHABLE in play** — `$AA17`/`$AA23` bound X to [2,26] and Y to [3,19] — so it must be **BUILT** (§23).

MEASURED on boss.pkl (`$A839=9`, `$A8DB=20`): 128 display writes plus 16 attribute writes `$5934/5/6/7 = 04 04 04 04`, `$5954.. = 04 07 04 04`, `$5974.. = 06 06 0E 0C`, `$5994.. = 02 0C 0C 22` — the block verbatim, bottom-right first.

## 7. THE ERASE — AND WHY IT IS NOT A RESTORE

`$A9DA` (the only caller is `$AA0E`; 72 entries in 240 frames on boss.pkl) reads Y **once**, then erases rows Y, Y+1, Y+2, Y+3 by entering **`$A929`** — *not* `$A925` — with A = the row. The PUSH/POP around the calls is necessary because `$A929`'s LDIs mangle BC. The DJNZ is an **8-bit decrement**, not a for-loop (TRAPS #45).

**`$A929` — one char row, 8 × 4 bytes from the `$E000` display shadow.** Table index `($FD00 + ((2*A)&$FF))`; destination = rowbase + `(($A8DC<<8)|($A8DB))`; source = destination + `$A000`. Eight pixel rows of four bytes, and because **both pointers are PUSHed and POPped**, the draw's E-carry hazard **does not exist here**: the walk is a clean 4-byte run from a base that steps only in the high byte.

**`$A951` is NOT AN ENTRY POINT** — census: zero `CD 51 A9`, zero `C3 51 A9`. ## 8. BOSS ↔ PLAYER — AND THE MOST DANGEROUS BYTES IN THE SUBSYSTEM

**`$A969` is boss↔PLAYER overlap, not bolt collision.** The old SPEC already says so (its "Refuted render-facet claims" block) and this pass confirms it; what nobody had was the rule.

**THE RULE [MEASURED].** B = boss Y tile, C = boss X tile. **P2 (`$FD8A`) is tested FIRST**; if it hits, `RET c` with `IX = $FD8A`. Otherwise `IX = $FD80` and the same code runs for P1. Per player: `OR A` clears carry, `BIT 7,(IX+7)` is the in-play test (`RET z` = no carry), then the Y axis `((IX+6)` vs B`)` and **only on success** the X axis `((IX+5)` vs C`)`. Driven on boss.pkl with `$A98F/$A990` forced to `00 00`, a full 32×24 sweep at **two** boss positions (20,9) and (2,3) — TRAPS #49's lesson — the accepted set is **exactly** `(tx-bx, ty-by) ∈ {0,1,2,3} × {0,1,2,3}`, identical at both. **The player is a POINT at its top-left tile against the boss's own 4×4 footprint**; its 16×16 body contributes nothing, and the one case that would make it matter (`t+1 == d`, the player one tile above/left) is **NOT** a hit. P2-first verified: with P1 out of play and P2 on the boss, carry = 1 and IX comes back `$FD8A`.

**The per-axis comparator `$A991` pushes `$A9AF` (SCF/RET) as a synthetic "hit" exit**, so every `RET z` lands there and returns carry. It tests `t == D, D+1, D+2, D+3` (D INCremented in place), then `t+1 == D+3, D+2, D+1` — **the same three cells, so the last three compares are DEAD CODE**: no 8-bit wrap can reach them (t ≤ `$1F`, D ≤ 26). The miss path POPs the pushed `$A9AF` into AF, `OR A`, `RET`. **Declare `$A9A3..$A9AB` dead and say why**; do not transliterate it.

`$9F5C` is `A := (A >> 3) & $1F`. The `RRA`s rotate **through carry**, but `AND $1F` masks the incoming bits off, so the result is carry-independent. Transliterate as `(px >> 3) & 31`, **not** `px >> 3` — the mask is what makes it safe and is also what makes `$A9A3` unreachable. Note `$9F62` (the boss HP) is the very next byte, and `$9F61` being a `RET` is what makes `$9F62` a plain variable rather than an operand.

### `$A98F/$A990` — RUNTIME-WRITTEN BYTES INSIDE `$A969`'s CONTROL FLOW

`$A987 CD 8F A9 CALL $A98F`. **The tape holds `37 C9` = SCF / RET, so `$A969` returns CARRY UNCONDITIONALLY — every position is an overlap.** The round-80 dump and boss.pkl / bossspawn.pkl / r50_48 / water / peachfall all hold `00 00` = NOP NOP, falling into the real comparator at `$A991`; round1_48 holds `00 69`.

**THE WRITER, AND WHY IT IS A BUG.** `$AAA1 DEC (HL)` in the slot walker `$AA60`. `$AA7B` copies `($AA57)` into `$B57C`, which counts DOWN to 1; inside, `$AA8C LD A,($AA57) / SUB 2 / SUB (HL) / LD C,A / LD B,0 / $AA95 LD HL,$A891 / ADD HL,BC` — an **8-bit subtraction placed in a 16-bit offset with B forced to 0**. For the two PLAYER slots `C` is −1 and −2, which become `$FF`/`$FE`, so HL lands **255 and 254 bytes FORWARD**, at `$A990` and `$A98F`, instead of behind `$A891`. MEASURED HL at `$AAA1` over 600 frames of play1p48: `{$A891:50, $A892:70, $A893:90, $A98F:55, $A990:201}`.

**The decay [MEASURED]:** on play1p48 (round 1, which still holds `37 C9`) exactly **55 = `$37`** decrements of `$A98F`, reaching 0 at frame ~110, and exactly **201 = `$C9`** of `$A990`, reaching 0 at frame ~429; same shape on play1p (41/187 remaining, both zero by frame 374); **zero** decrements in 600 frames on title.pkl. - **#67 — A SHIPPED STATE CAN BE A MID-ROUTINE CAPTURE.** `build/bottle.pkl` resumes inside `$89CB` with `A`, `HL`, `DE` and a return address already loaded, and completes a spawn with the pre-poke type. Check the saved PC and the stack before attributing a routine's tail to your input. (§17)

- **#70 — A RUNTIME-WRITTEN BYTE CAN BE AN OPCODE IN SOMEBODY ELSE'S CONTROL FLOW.** `$A98F/$A990` decay from `SCF/RET` to `NOP/NOP` under an index underflow in an unrelated walker, and the tape value makes every overlap test return TRUE. ## 7. THE DRAW `$A8C1` — A 4×4 BLIT WHOSE X COORDINATE IS NEVER LOADED

`$A8C1` is the only routine that puts the 32×32 special object on the screen. It has exactly **two callers and no jump entries** — `CD C1 A8` at `$A844` and `$AA29`, `C3 C1 A8` zero hits, full addressing-form census over `build/image_tape.bin` [MEASURED]. On round 80 the first of those is dead (§12), so `$AA29` is the whole of it: 49 entries in 161 frames of live `boss.pkl`, `$A844` = 0 [MEASURED, 1.2M-instruction profile, round `$50`].

**Geometry.** Four character rows, each eight pixel rows of four bytes: `LDI ×4 / DEC E ×4 / INC D`, `$A8E1..$A8EF`, counted down by `A`; the outer four-count lives in `A'` across `EX AF,AF'` at `$A8D3`/`$A8F7`, and `A` itself is destroyed by the inner loop. **128 display bytes**, source contiguous, 32 bytes per character row. Driven on `boss.pkl` (round `$50`, `$A839` = 9, `$A8DB` = 20): 128 writes `$4834..$4F97`, all 128 addresses distinct, plus 16 attribute writes — **144 per frame, not 128** [MEASURED]. Across all 425 legal placements (§12) the count and the distinctness hold: 425/425 with 128 distinct bitmap bytes and 16 distinct attribute cells [MEASURED].

**The blit is OPAQUE.** `LDI` with no mask and no read of the destination [READ]. Nothing behind the boss survives its 16 cells; that is what makes the erase (§10) load-bearing rather than cosmetic.

**`$A8C2/$A8C3` — SMO #1, the source.** `$A8C1 11 00 5B LD DE,$5B00` is the instruction; the operand is live state. Sole writer `$A87D` inside the frame-select `$A84D` — census: `22 C2 A8` once, `32 C2 A8` / `ED 43|53 C2 A8` / `DD|FD 22 C2 A8` zero [MEASURED]. Tape `$5B00`, `boss.pkl` `$FE02`, `bossspawn.pkl` still `$5B00`. **There is no `LD A,($A8C2)` anywhere in 64K**: an operand grep for readers of the source pointer returns nothing, because the read *is* the instruction fetch.

**`$A8DB/$A8DC` — SMO #2, the X tile, and the sharpest fact in this section.** `$A8DA 01 00 00 LD BC,0` supplies the X offset, added 16-bit at `$A8DD ADD HL,BC`. A full addressing-form census of `$A8DC` over 64K returns **zero hits in every form** — `32/3A/22/2A/21/11/01/ED 43/ED 53/ED 4B/ED 5B/DD 21/FD 21/CD/C3` [MEASURED]. It has no writer, no reader and no pointer load. It is nevertheless live: **`$A934 2A DB A8 LD HL,($A8DB)` in the erase reads the pair as a 16-bit word**, so the same two bytes are consumed as an *instruction operand* by the draw and as *data* by the erase. Built on `boss.pkl` with `$A8DC := 1`: the draw moves from `$4834..$4F97` / `$5934..$5997` to `$4934..$5097` / `$5A34..$5A97`, and the erase moves with it, identically [MEASURED]. **A port that models the boss X as an 8-bit tile is right until something writes `$A8DC`, and nothing ever will — which is exactly why the field is easy to drop and impossible to catch.**

**The E-carry drift, and its real threshold.** `LDI`'s `INC DE` is sixteen-bit; the four `DEC E`s at `$A8E9` are eight-bit and `INC D` at `$A8ED` is eight-bit. When a four-byte run *ends* at low byte `$FF` the carry is already in D and the `DEC E`s cannot take it out, so the destination drifts **+$100 per pixel row**. The trigger is `rowbase_low + X + 3 ≥ $100`, i.e. character rows 7/15/23 (`$FD00` entries with low byte `$E0`) with **X ≥ 28** — not 29, as the cluster model has it. MEASURED at Y = 12 on `boss.pkl`, per-character-row extents:

| X | rows 12/13/14 | row 15 |
|---|---|---|
| 27 | normal | `$48FB..$4FFE` (no drift) |
| 28 | `$489C..$4F9F` … | **`$48FC..$56FF`** |
| 29 | `$489D..$4FA0` … | **`$48FD..$5700`** |
| 31 | `$489F..$4FA2` … | **`$48FF..$5702`** |

Row 15 at X = 29 writes `48FD 48FE 48FF 4900 | 4AFD 4AFE 4AFF 4B00 | 4CFD … | 4EFD …` — the pixel rows step **$200** apart, and the *first* row is already split across two pages [MEASURED]. **UNREACHABLE in play**: `$AA17 LD BC,$1B02` and `$AA23 LD BC,$1403` bound X to [2,26] and Y to [3,19], two short of the threshold. It must be BUILT.

**The attribute fall-through `$A8FC`, and SMO #3.** `$A8FC 11 81 A8 LD DE,$A881`; `$A8FD/$A8FE` is a self-modified 16-bit pointer, sole writer `$A869 22 FD A8` (census: one hit; `32 FD A8`, `ED 43|53 FD A8` zero) [MEASURED]. `$A8FF INC D / $A900 DEC D / $A901 RET z` skips the attribute pass when the high byte is zero — **DEAD in play**, because `$A869` can only ever produce `$A8xx`/`$A9xx`; shown only by building it: `$A8FE := 0` on `boss.pkl` drops the draw from 144 writes to **128, with zero attribute writes** [MEASURED].

The address arithmetic is `$A902 LD A,H / DEC A / RRA ×3 / AND 3 / OR $58 / LD H,A`, then `$A90C INC L ×3`. **The input register is H, not D** (SPEC (b) had D). `L` is *unchanged* — the screen low byte is the attribute low byte — and the three `INC L` are eight-bit. Then four rows of `LDD ×4` with the destination stepping down 4 (sixteen-bit `DEC DE` inside `LDD`) and up 32 (`$A91B LD BC,$FFE4 / ADD HL,BC`, sixteen-bit).

**The pass runs ONCE per draw, not once per character row.** Profile on `boss.pkl`: `$A8C1` = 16, `$A8FC` = 16, `$A902` = 16 [MEASURED]. It derives its address from the **last** character row's pointer and walks *up*; the erase derives one per row and walks *down* (§10). That single difference is the whole of §8's HUD defect and §10's right-edge divergence.

**The write order is bottom-right first and is NOT observable in play.** `boss.pkl` at (20, 9): `5997=22 5996=0C 5995=0C 5994=02 | 5977=0C 5976=0E 5975=06 5974=06 | 5957=04 5956=04 5955=07 5954=04 | 5937=04 5936=04 5935=04 5934=04` — the 16-byte block verbatim, reversed [MEASURED]. Since all 16 addresses are distinct in all 425 legal placements [MEASURED], a port may write them in natural order. Outside the box it may not: see §8 and §10.

## 8. THE `$FD00` ROW TABLE — RUNTIME-BUILT, AND A HUD GUARD THAT IS BITMAP-ONLY

The table is 64 little-endian words, `$FD00..$FD7F`, indexed by `$A8CB LD IX,$FD00 / ADD IX,BC` (draw) and `$A92D LD DE,$FD00 / ADD HL,DE` (erase). **Do not census it by byte-grepping the word `00 FD`** — that returns 90 addresses in the tape image, of which the two I disassembled and confirmed as table indexers are the two above; `$9D5C`, `$9D72`, `$9D8B`, `$99FF`, `$966F` and most of the rest are `NOP`/`LD (IY+…)` coincidences [MEASURED, the same error class as the `$8309` "ten writers"].

### It is not tape data in the way the cluster model says

`$FD00..$FD7F` is byte-identical in `build/image_tape.bin` and `build/image.bin`, and `bleepload` starts from a zeroed buffer, so it *is* tape-sourced. **It is also rebuilt at cold start, and the constructor had never been read.** `$963B..$9685`, in the same straight-line chain as `IM 2` and H0's `$96A5` relocation:

```
963B 21 00 FD   LD HL,$FD00
963E 01 80 00   LD BC,$0080          <- B = 0, C = $80
9641 CD 49 AA   CALL $AA49           <- XOR A / LD (HL),A / INC HL / DJNZ  -- counts with B
9644 FD 21 00 FD LD IY,$FD00
9648 21 00 40   LD HL,$4000 / CALL $9662
964E 21 00 48   LD HL,$4800 / CALL $9662
9654 21 00 50   LD HL,$5000 / CALL $9662
965A 21 00 00   LD HL,$0000 / CALL $9662
9662 06 08      LD B,8
9664 FD 75 00   LD (IY+0),L / LD (IY+1),H      <- the DISPLAY half
966A 7C C6 A0   LD A,H / ADD A,$A0
966D FD 75 40   LD (IY+$40),L / LD (IY+$41),A  <- the SHADOW half, 32 entries on
9673 3E 20 85 6F LD A,$20 / ADD A,L / LD L,A
9677 FD 23 FD 23 INC IY ×2 / DJNZ $9664
967E F3         DI
967F 21 FF 01   LD HL,$01FF
9682 22 00 FD   LD ($FD00),HL
9685 22 02 FD   LD ($FD02),HL        <- the HUD patch: DISPLAY HALF ONLY
```

**MEASURED**, driven on round 80 (`boss.pkl`, constructor bytes restored from `image_tape.bin`, SP pinned to `$8FF0`, `interrupts=False`, `$FD00..$FDFF` poisoned with `$5A`): 1179 steps from `$963B` to `$9688`, and the rebuilt `$FD00..$FD7F` is **byte-identical to the tape image**. Three facts fall out of it, and two of them are new:

1. **`LD BC,$0080` clears 256 bytes, not 128.** `$AA49` counts with `B`, and `B` = 0 from that operand. MEASURED: all 128 poisoned bytes of `$FD80..$FDFF` — **the entity array**, not the table — came back zero. Same idiom as H3's `$7C46 LD BC,3` (768, not 3). A port transliterating the immediate as a length is wrong by a factor of two and clears the wrong object.
2. **The `$01FF` patch touches only four bytes**, offsets 0..3, i.e. the display half's entries 0 and 1. Stopped before `$967E`, the table holds `entry[0] = $4000`, `entry[1] = $4020` — the real HUD rows [MEASURED].
3. **`entry[i+32] == entry[i] + $A000` is FALSE for i = 0 and 1**, and the cluster model's "exactly, across all 64 entries" is wrong. `entry[0] = $01FF` against `entry[32] = $E000`; `entry[1] = $01FF` against `entry[33] = $E020` [MEASURED, both images]. It holds for the other 62. The shadow half has *no* HUD guard, because `$966D` builds it from `H + $A0` *before* the patch runs. Anything that blits to the shadow through entries 32/33 writes the real shadow of HUD rows 0 and 1.

**The constructor is unreadable in every live state.** `boss.pkl` at `$963B` holds `00 00 00 00 00 00 00 00 C9` — `$8CC4 LD SP,$96DD` parks the stack over it, exactly as `tools/provenance.py` records for `$96A5` [MEASURED]. Running it required restoring `$9600..$96AF` from the tape image first.

### The HUD guard protects the BITMAP and nothing else — in two different ways

Entries 0/1 send pixel writes to `$01FF`, below `$4000`, where they are discarded. Entries 24..31 (`$0000..$00E0`) are the same kind of sink for rows that do not exist. **But both `$A8FC` and `$A951` derive the attribute address from the screen HIGH byte**, and `$01FF`'s high byte is `$01`, which the `(H-1)>>3 & 3 | $58` map sends into `$58xx`/`$59xx`. Driven on `bossspawn.pkl` (round `$50`, `$A839` = 0, `$A8DB` = 14):

| | bitmap writes ≥ `$4000` | attribute writes | where they land |
|---|---|---|---|
| **erase** `$A9DA` | 64 (rows 2, 3 only) | 16 | `$590D..$5910` **twice**, then `$584E..$5851`, `$586E..$5871` |
| **draw** `$A8C1` | 64 (rows 2, 3 only) | 16 | `$580E..$5811`, `$582E..$5831`, `$584E..$5851`, `$586E..$5871` |

[both MEASURED]

**They break the HUD in two different ways, and the difference is the derivation.**

- The **erase** derives per character row. Rows 0 and 1 both compute destination `$01FF + 14 = $020D` — *the carry out of `$FF` lands in D* — so after eight `INC D` the row is `$0A`, and `(D-1)>>3 & 3 | $58` gives `$59`, `E` = `$0D`. Both rows alias to **attribute row 8, column 13** (X − 1), and the second pass is an exact duplicate of the first. Single-stepped: the eight destinations are `$020D, $030D, … $090D`, twice [MEASURED].
- The **draw** derives once, from the last character row (row 3, a real `$40xx` address), then walks *up* by 32 — so it writes attribute rows 3, 2, **1 and 0**: `$582E..$5831` and `$580E..$5811` are the genuine HUD attribute cells [MEASURED].

**The erase's shadow source at row 0 is not the shadow.** `$A939 LD HL,$A000 / ADD HL,DE` gives `$A000 + $020D = $A20D`. Single-stepped: the eight source pointers are `$A20D, $A30D, … $A90D` — **game code in the `$A2xx..$A9xx` region**, read and thrown at ROM [MEASURED]. Harmless, but a port that "clips" instead of sinking has also silently changed which bytes were read.

**TRAP CANDIDATE, for the list in §24.** *The harness cannot tell a sink from a clip.* The row-0 bitmap writes produce **zero** entries in `Mem`'s write log, **zero** increments of `Mem.rom_writes`, and leave `$0100..$0BFF` byte-identical [all three MEASURED]. SkoolKit's block-move path discards the sub-`$4000` write without going through `Mem.__setitem__`. So a gate that proves "the sink was exercised" by watching writes proves nothing, and a port that clips the loop instead of running it passes. The gate must assert the **side effects** — the attribute writes at `$590D` and the loop's own pointer advance — never the absence of bitmap writes.

**What a port must carry.** The 64 words as an asset (or the constructor: both produce the same bytes), **rows 0/1 as a performed-and-discarded write**, the attribute derivation left *unguarded*, and the shadow half's entries 32/33 pointing at `$E000`/`$E020` rather than at `$01FF + $A000`.

## 9. THE `$A890` ATTRIBUTE-BLOCK ARRAY — AND THE LIVE-STATE HOLE AT C = 1

## 10. THE ERASE `$A9DA → $A929 ×4 → $A951` — A SECOND, DIFFERENT DERIVATION OF THE SAME SIXTEEN CELLS

```
A9DA 3A 39 A8 LD A,($A839)   ; Y read ONCE
A9DD 4F       LD C,A
A9DE 06 04    LD B,4
A9E0 C5       PUSH BC        ; $A929's LDIs mangle BC
A9E1 79       LD A,C
A9E2 CD 29 A9 CALL $A929
A9E5 C1       POP BC
A9E6 0C       INC C
A9E7 10 F7    DJNZ $A9E0     ; EIGHT-BIT decrement, not a for-loop (TRAPS #45)
A9E9 C9       RET
```

Sole caller `$AA0E`; 49 entries in 161 frames on `boss.pkl` [MEASURED]. Rows Y, Y+1, Y+2, Y+3.

**`$A929` is the entry, `$A925` is the routine head, and `$A951` is neither.** Census over 64K [MEASURED]: `CD 29 A9` once (`$A9E2`), `C3 29 A9` zero; `CD 25 A9` zero, `C3 25 A9` once (`$A84A`); **`CD 51 A9` zero and `C3 51 A9` zero** — `$A951` is reached only by falling out of `$A929`'s pixel loop and can never be called. `$A925` (`LD A,($A839) / DEC A`) erases the single row the *giant item* has just vacated, and is dead on round 80 (§12).

**`$A929`, one character row.** Index `$FD00 + ((2*A) & $FF)`; destination = rowbase + the **sixteen-bit** `($A8DB)`; source = destination + `$A000`, the `$E000` display shadow. ## 11. `$9D4C` — NOT A RESTORE, AND THE COLOUR SHADOW IS NOT A BOOLEAN

```
9D4C CB 6E     BIT 5,(HL)        ; HL = the COLOUR SHADOW cell, $F800 + offset
9D4E 3A 09 83  LD A,($8309)      ; the round's OPEN attribute
9D51 28 03     JR z,$9D56
9D53 3A 0A 83  LD A,($830A)      ; the round's SOLID attribute
9D56 12        LD (DE),A         ; DE = the real $58xx cell
9D57 C9        RET
```

A pure function of (colour-shadow bit 5, `$8309`, `$830A`) owning no state. **It is not a restore**: `$F8xx` is never copied to `$58xx`; the attribute is *reconstructed*. A port that copies the shadow back paints `$00`/`$20` — black on black.

**Both arms, measured twice over, on round 80.** `boss.pkl` (Y = 9, X = 20): all 16 shadow cells `$00`, all 16 attributes written `$46 = ($8309)`. `bosshit.pkl` (Y = 9, X = 24): `$F958`/`$F959` are `$20` and `$5958`/`$5959` are written `$66 = ($830A)` while the other fourteen get `$46` [both MEASURED].

**Gated over the input range, TRAPS #46 style, TRAPS #44 respected.** On `boss.pkl` I seeded the boss's sixteen colour-shadow cells with sixteen *different* values spanning the byte — `00 01 1F 20 21 3F 40 41 5F 60 7F 80 A0 C0 E0 FF` — and poisoned all sixteen attribute cells to `$5A` first so that no write could be invisible. `h.call($A9DA)`: **all sixteen cells written, 16/16 match `(seed & $20) ? ($830A) : ($8309)`, zero mismatches** [MEASURED]. Note `$40 → $46` and `$C0 → $46`: bits 6 and 7 set with bit 5 clear still reads OPEN.

### The cluster model's "$F8xx holds exactly $00 or $20 by play time" is WRONG

Value census of the colour shadow `$F840..$FAFF` (704 bytes, attribute rows 2–23) [MEASURED]:

| state | round | distribution |
|---|---|---|
| `boss` | `$50` | `00`×540, `20`×60, `40`×2, `60`×40, `A0`×20, `E0`×42 |

Six to eight distinct values, not two. This is H4 and H5 showing through: **bits 6/7 are the bubble drift field** (H4, read by `$B846`'s `RLCA ×3 / AND 6`) and **bits 0–4 are the occupancy field** (H5). `$40` is *open with a drift bit*; `$0B`/`$0C` are *open with occupancy bits*. `$9D4C` masks all of them off and asks one question.

**So the correct statement is the inequality, not the equality**: `$9D4C`'s input is `(shadow & $20) != 0`, H3's solid flag, and the other seven bits are live fields owned by other subsystems. **A port that stores the colour shadow as a boolean loses the drift and occupancy fields; a differential gate that compares whole shadow bytes will see legitimate differences that are not render bugs.** This also preserves H3's distinction: `$9D4C` reads the *transformed* shadow, where bit 5 alone is legitimate; H3's `attr & $38` rule is about the *raw* build attributes and is not the same test. Do not unify them.

**`$9D4C` has five call sites — and on the boss round exactly one of them fires.** Census: `CD 4C 9D` at `$9CFC`, `$9D01`, `$9D0B`, `$9D10`, `$A961`; `C3 4C 9D` zero [MEASURED]. ## 12. CADENCE, THE DEAD GIANT-ITEM PATH, AND WHAT A PORT MUST CARRY

### The boss is not repainted every frame

`$A9ED` is entered ~10 times per frame and `$AA05 LD A,1 / INC A / AND $1F / LD ($AA06),A / RET nz` passes one entry in 32 (`$AA06` is **SMO**, a 5-bit phase counter over main-loop passes). The body `$AA0E` is **ERASE at the current position → bounce X → bounce Y → DRAW at the new position**, 288 writes.

**MEASURED over 600 frames of live `boss.pkl` (round `$50`)**, write-watching `$A839`: **178 move bodies**, sole writer PC `$AA45`, = **0.2967 per frame**; gap histogram 3 frames ×114, 4 ×61, 5 ×2. Independently, the 1.2M-instruction profile gives `$A8C1` = 49 in 161.1 frames = 0.304 [MEASURED].

Consequences a reader misses:

- **Between move frames nothing touches the boss's 16 cells.** Anything else that draws over the boss stays broken until the next move. A sampler at the main-loop top sees the boss image unchanged on roughly two frames in three; a differential must run long enough to cross a move.
- **`$AA06` is state.** Carry it, or the two engines phase-apart on frame 1 and every subsequent comparison is noise.
- **The erase reads the live `$A839`/`$A8DB`, not a cached previous position.** There is no cached position anywhere in this subsystem — unlike the per-entity render (M7.3b), which erases at a cached position and draws at the current one. The boss erases and draws inside one body, which is why the ordering (erase *first*) is load-bearing and why a port must not "optimise" it into a single repaint.

### The giant-item half of the same code is dead on round 80

### What a port must carry that a reader would miss

1. **`$A8DC`**, the X high byte with zero references in 64K. A capture always reads 0; dropping it is invisible until a gate builds it.
2. **The sixteen-bit/eight-bit split in the draw's inner loop.** Transliterating `LDI` as "copy 4 and step back 4" loses the drift permanently — and the drift is the only thing that distinguishes a faithful blit from a clipped one at X ≥ 28.
3. **The `$01FF` sink performed, not clipped** — with the attribute derivation left unguarded, so rows 0/1 corrupt the HUD attributes the way §8 measures. And note the harness cannot catch a clip.
4. **Two separate attribute derivations**, one per draw (from the last row, walking up) and one per erase row (from that row's own D, walking right). Sharing code between them is correct in play and wrong everywhere else.
5. **`$9D4C` as a reconstruction from `(shadow & $20, $8309, $830A)`**, never a copy — and the colour shadow kept as a full byte, because bits 0–4 and 6–7 belong to H5 and H4.
6. **The block pointer derived as `$A890 + ((16·C) & $FF)` addressing the block's LAST byte**, not a hard-coded per-frame colour table — the array has a live-state hole at C = 1 and its own opcodes at C ≥ 4.
7. **The six SMOs**: `$A8C2/$A8C3` (source), `$A8DB` (X), `$A8DC` (X high, writerless), `$A8FD/$A8FE` (block pointer), `$A85C` (frame index), `$A839` (Y — simultaneously `$A838`'s operand *and* a variable read by six absolute loads), `$AA06` (phase), plus the data bytes `$AA47`/`$AA48`.

## 13. THE `$5B00` PAGE — FOUR USES OF THE SAME BYTES, AND WHEN EACH IS LIVE

`$5B00` is not one thing with four names. It is **one page of RAM that four subsystems write and read in overlapping time windows**, and the only correct way to state any claim about it is to say *when*.

**Use 1 — cold start, once per power-on.** `$96A5 LD HL,$E000 / LD DE,$5B00 / LD BC,$06A8 / LDIR` relocates 1,704 bytes. **H0 measured this** (1,704 writes, every one from PC `$96AE`, contiguous; and it is a *copy*, proved by poking `$E680/$E681` and reading `$6180/$6181` back). Two consequences carried forward here, not re-derived: `build/image_tape.bin` read at `$5B00` is wrong by 1,385 of 1,704 bytes (TRAPS #43), and the projectile sprite bank `$6000..$617F` — **all zero in the tape image at its own address** — is tape data living at `$E500..$E67F`. A port that reads `$6000` from the tape image and concludes "runtime-built" has invented a fact. [H0, MEASURED]

**Use 2 — every round build.** `$8390 LD IX,$5B00 / LD HL,($860D) / LD A,($860C) / OR A / JR nz,$83B4` fills **all thirty-two bytes `$5B00..$5B1F`** with the round's platform tile, in one of two modes selected by `($860C)`: the `$839D` mode writes each of 8 source bytes into `(IX+0)`,`(IX+1)`,`(IX+$10)`,`(IX+$11)` with IX advancing 2 — two identical 16-byte halves; the `$83B4` mode is H8's linear `hi, lo, hi, lo` interleave. **H8 read, transliterated and gated both** (`tools/roundtile.py`, `build/roundtile_fixture.json`), including the correction that `$83D9` is CALLed twice and `$83C5..$83D3` copies the pair forward with `LD A,(IX-2)`. **Use 3 — the two projectile slots, for the rest of the round.** Immediately after the tile fill, `$986C CALL $A36C` re-zeroes **twenty bytes, not thirty-two**: `$A36C LD HL,$5B00 / LD B,$14 / CALL $AA49`, then `LD HL,$FDEE / LD B,$14 / JP $AA49`. ## 14. THE PROJECTILE PASS — `$9AEB → $9AFC → $9B07`, AND THE PER-SLOT BODY

### The clock, and why it is not `$AA60`'s clock

`$8D58 CALL $9AEB` sits in the main-loop chain at `$8D40`, which runs many times per video frame. `$9AEB` gates itself down twice:

```
$9AEB  LD A,($8DBD)      ; low byte of the 16-bit ISR frame counter
$9AEE  LD HL,$A37C
$9AF1  CP (HL) / LD (HL),A / RET z     ; frame EDGE DETECTOR -> once per video frame
$9AF4  LD A,n            ; n IS $9AF5 -- SMO, the parity latch
$9AF6  XOR 1 / LD ($9AF5),A / RET z    ; involution -> once per TWO video frames
$9AFC  LD IY,$5B00 / CALL $9B07 / LD IY,$5B0A / (fall through)
```

Profiled 400,000 instructions on two worlds:

| world | `$8D58` calls | `$9AEB` | `$9AFC` (the body) | `$9B07` | frames (`$8DB5`) | `$AA60` |
|---|---|---|---|---|---|---|
| `r50_48` (round 50) | 230 | 230 | 24 | 48 | 46 | 23 |
| `boss.pkl` (round 80) | 539 | 539 | 27 | 54 | 54 | 27 |

[MEASURED, `h.profile(400_000)`, both rounds ≥ 2]

**Both `$9AFC` and `$AA60` land on 0.5 per video frame, and they get there by completely different clocks.** `$AA60` runs on the **odd ISR branch** (correction 3; `web/game.js` already has this). `$9AFC` runs on a main-loop chain entered 5–10× per frame, cut to once per frame by a frame-edge detector on `$8DBD` and halved again by an SMO parity latch. `$9B07` is exactly 2× `$9AFC` because slot 0 is a `CALL` and slot 1 is fall-through. A port that puts the projectiles on the odd ISR reproduces the *rate* and diverges in *phase*, and diverges outright the moment the main-loop pass count per frame changes — which is exactly what a slowdown flag does.

**`$A37C` is not scratch.** It is the **global animation phase** that `$9C92` (kind 5's four spin frames) and `$9D65` (the bit-1 sprite toggle for kinds 6/7/8) both read. It is also the byte immediately below the bolt sprite `$A37D..$A39C`, so **an extraction of "34 bytes from `$A37C`" picks up live state**; extract 32 bytes from `$A37D`. [READ + census]

### `$9AE7..$9AEA` is data, and `$9AFD` does not exist

### `$9B07` — run it, or try to fill it

### `$9B1E` — the enemy-shot spawn, all ten conditions

In order, and the order matters because condition (6) destroys the pointer condition (5) used:

1. `$9B1E BIT 7,(IX+7) / RET z` — the player in IX is in play.
2. `$9B23 BIT 2,(IX+$5A) / RET nz` — and not dying.
3. `$9B28 CALL $FE85 / AND 7 / RET z` — `r = PRNG() & 7`; `r == 0` aborts.
4. `$9B2E DEC A` — `idx = r − 1`, so **idx ∈ 0..6 and enemy slot 7 can never be chosen.**
5. `$9B31 LD A,($AA57) / SUB 3 / CP C / RET c` — `idx ≤ ($AA57) − 3`. F0 settled `$AA57 = enemies + 2`, never outside 5..9, so the bound is `(live enemies) − 1`.
6. `$9B3C LD HL,$B562 / ADD HL,BC` with `C = 2*idx`; `$9B41 CP 1 / JR z / CP 5 / RET c` — **kind must be 1 or ≥ 5.**
7. `$9B49 CALL $9B70 / RET nz` — the enemy qualifier, below. It returns with **HL pointing at enemy+6**, which is why the fill that follows walks `HL+1`, `HL−1`, `HL−1` instead of re-reading `$B562`.
8. Fill: `+8 := kind`; `SET 1,(HL)` on enemy+7 — **the claim flag**; `+7 := $C0 | (enemy facing bit 0)`; `+6 := (enemyY & $F8) | 1`; `+5 := enemyX`; `+9 := enemyX & $F8`.

**`+0/+1` are not written here.** The first handler tick writes the sprite pointer, so a freshly spawned slot carries a stale pointer for its first tick. [READ; the cluster measured `spr = 0000` for the first two frames of every spawn]

`$B562..$B571` is the per-enemy shot-kind table, **stride 2, only the even byte used**, written at the round build by `$730E LD (IX+$10),A` with `A = (spawn X byte) & 7` — the enemy's type. `$9B3D` is its only code reference in 64K. The cluster gated it causally: `$B562 := 1` on `r50_48` made enemy 0's shot come out kind 1 while the rest stayed kind 5; poking the **odd** bytes `$B563/$B565` changed nothing — the control that pins the stride at 2. [MEASURED, round 50]

### `$9B70` — the qualifier, and the write nobody expects

`E` = enemy index on entry; returns Z to accept.

- `$9B73 LD BC,$A891 / ADD HL,BC / LD A,(HL) / OR A / RET nz` — the **eight-byte cooldown array must be zero** for this enemy. `$7385` builds it at `$7461 + 8*(A&7)` plus `$1E`; `$8888` fills all eight with `$FF` (the power-up shoot lock, reached by handlers 10 *and* 11 — I11's correction); `$900B` fills with `$64`; `$AA9C/$AAA1` decrement it in the per-enemy pass.
- `$9B7B` — `HL = $FD9B + 10*E`, an **eight-bit** multiply (`E*2 → L`, `*4`, `*8`, `+L`) widened only afterwards.
- **`$9B87 LD (IY+4),L` fires HERE, before the remaining five tests.** A *rejected* spawn attempt still stamps the slot's `+4`. This is not a curiosity: it is visible in a shipped capture — the cluster found `$5B0E = $C3` on a live `r50_48` world whose slot 1 was inactive. A port that writes `+4` only on success leaves a byte different from the machine, in a byte the giant-diamond blit reads (§13).
- `$9B8A LD A,(HL) / OR 1 / RET p` — enemy +7 bit 7 set; `BIT 3,A / RET nz`; `BIT 1,A / RET nz` — not already claimed.
- `$9B94 INC HL ×2 / INC (HL) / DEC (HL) / DEC HL ×2 / RET nz` — enemy `+9 == 0`, tested by a **non-destructive INC/DEC pair that performs two real writes** to enemy+9 with the value unchanged. TRAPS #44 in miniature: a byte-diff oracle sees nothing here, and a port that models it as a read is right about the value and wrong about the write count.
- `$9B9B` — enemy `+6` low 3 bits zero (Y 8-aligned).
- `$9BA0 CP 7 / JR z,$9BB1` — **kind 7 is exempt from the row test** and takes the `XOR A` exit that forces Z. Every other kind requires `(enemy+6 & $F8) == ((IX+6) & $F8)`.

The cluster's built-world gate is the right shape and its headline number is itself a result: **7 spawns per 60 calls** with seven live enemies, then silence — because `$9B70`'s `SET 1,(HL)` locks each enemy after one shot. Row-mismatched kind 1 gives 0; row-mismatched kind **7** gives 7; every single-condition violation gives 0. [MEASURED by the cluster, round 50, `$9B1E` called directly with SP pinned and `interrupts=False`]

### `$9BB4` is the per-tick body, not an abort path

```
$9BB4  LD A,(IY+6) / PUSH AF / AND $F8 / LD (IY+6),A
$9BBD  CALL $A314              ; the 16x16 erase -- SHARED WITH THE BOLT (see 16)
$9BC0  POP AF / LD (IY+6),A
$9BC4  LD A,(IY+8) / CP 8 -> $9CF4 / CP 7 -> $9CDC / CP 6 -> $9C4B / CP 5 -> $9C8C / DEC A -> $9BE3

Erase first, then dispatch. **The Y is forced 8-aligned across the erase and restored**, which matters only for kind 1, whose low 3 Y bits are a launch phase — the erase always addresses the character row, never the phase-offset row. The abort is `$9D58`, not this. [READ; the cluster drove all five arms]

The default arm zeroes `+8` **while leaving the ACTIVE bit set** — a permanent no-op loop. It is unreachable through `$9B1E` (which admits only 1 and ≥5) and `$9E1E` (which writes only 8), but a 57-state census found it *already present in shipped memory*: `boot.pkl`, `title.pkl` and `iball.pkl` all hold `$5B00/$5B0A +7 = $CE/$F0` with `+8 = 190/243`. ### `$9460` is a singleton, and it confirms the free list is unique

```
$9460  LD A,($A15A) / OR A / RET nz      ; n IS $A15A -- SMO, the singleton gate
$9465  LD A,($FECE) / OR A / RET nz

## 16. THE BOLT ON SCREEN — `$A314` ERASE, `$A2D5` DRAW, `$9D77` PHYSICS

**`$A314` is not the bolt physics.** The brief that produced the cluster called it that; it is the **16×16 shadow → display erase**, and it is shared with every `$5B00` projectile through `$9BB4`.

```
$A314  LD A,(IY+5) / CALL $9F5C / LD ($A355),A   ; SMO: tile X
$A31D  LD A,(IY+6) / LD C,A / AND 7 / LD ($A349),A ; SMO: band 3 = subY
$A326  LD A,8 / SUB B / LD ($A33D),A             ; SMO: band 1 = 8 - subY
       ... IX = $FD00 + 2*tileY ...
$A33B  LD A,B / LD B,n / CALL $A34D              ; n IS $A33D
$A341  XOR A  / LD B,8 / CALL $A34D
$A347  XOR A  / LD B,n / INC B / DEC B / RET z   ; n IS $A349 -- skips band 3 when subY == 0
```

**Three SMOs in nine instructions**, all three the band counts: `$A33D` (tape `$07`), `$A349` (tape `$00`), `$A355` (the operand of `$A354 LD A,n` inside `$A34D`, tape `$02`). `(8−subY) + 8 + subY = 16` exactly. The shadow is `display + $A000`, formed at `$A351 ADD A,$A0` on the **high** byte. [READ against `image_tape.bin`; geometry MEASURED by the cluster: X=`$50` Y=`$50` → 32 bytes over two char rows; X=`$50` Y=`$54` → 32 bytes over **three**]

**Two eight-bit walks a transliteration must reproduce as `(low & 0xFF)`, not `address + 1`.** `$A34D` does `INC E / INC L` for the second byte of the pair and `DEC E / DEC L` back; at tile X = 31 this **wraps inside the 256-byte page** (measured at X=`$F8` and `$FF`, painting (10,31), (11,0), (11,31), (12,0)). And `INC H / INC D` per pixel row is an eight-bit increment of the display high byte, correct only because each band is at most 8 rows.

**`$A2D5` draws, and ignores the sub-row.** `$A304` is the **SMO** tile X (operand of `$A303 ADD A,n`; tape `$2A`, round-80 dump `$06`). H comes from `(IX+1)` with **no `$A0` added**, so the draw goes straight to the display, transparently (`OR`) — which is exactly why the erase must restore from the shadow. **THE ASYMMETRY THE PORT MUST KEEP:** at Y=`$50` and Y=`$54` the draw hits the *same* four cells while the erase honours the sub-row and spans three. In play Y is always `&$F8` so they agree; "fixing" either one breaks the pairing. [MEASURED by the cluster on a cleared display: 22 bytes, the `$A37D` sprite's 22 non-zero bytes of 32]

**`$FD00..$FD33` is the single most important thing for the transliteration.** Twenty-six little-endian entries indexed by tile row. Entries 2..23 map onto the screen; **entries 0, 1, 24 and 25 point below `$4000`** (`$01FF`, `$01FF`, `$0000`, `$0020`). Writes there are discarded by the hardware, so neither routine needs clipping — a 16-pixel sprite straddling the top of the playfield or the bottom of the screen has its off-screen band written into ROM. **A JS port must reproduce the SINK, not a clip**, because the loop counters and IX advance regardless. Gate it by driving Y = `$00`, `$08`, `$B8`, `$BC` and asserting the **byte count**: at Y=`$B8` the erase writes 16 instead of 32 and the draw 11 instead of 22; at Y=`$00` both write zero. [MEASURED by the cluster]

H2 already paid for the mirror of this lesson from the other side — a repaint landing on table entries `$0000`/`$0020` is "dropped on the Spectrum but stored happily by a `Uint8Array`", which is why the engine carries a ROM guard.

**The physics is `$9D77`.** `(IY+7)` bit 0 selects the direction and the `SBC A,A / SUB 1 / ADC A,1 / ADD A,A ×3` chain produces exactly **+8 or −8**, eight-bit, **with wrap and no clamp** (`$00 → $F8` and `$F8 → $00` both observed). The bound is enforced afterwards at `$9ED3 CP 15 / JR c` and `CP $E7 / JR nc` → `$9F13 RES 7,(IY+7)`, the despawn. [MEASURED by the cluster across X = `$00,$08,$7F,$F8,$FF`]

**`$9D83` is a SELF-MODIFIED OPCODE, and the only place the speed lives.** Kind 1 writes `$00` (NOP) over the third `ADD A,A` to halve its step to 4 px, and restores it by **reading `$9D82` as a data byte** to recover `$87`. A grep for a speed constant finds nothing at all. Gate it by comparing kind 1's stride against kind 5's in the same world; 4 against 8 is the whole test.

### None of this is visible in any capture

| world | frames | `$9E50` | `$9E85` | `$9E90` | `$A314` | `$9F29` | `$9F56` |
|---|---|---|---|---|---|---|---|
| `boss.pkl` | 54 | 539 | 27 | 54 | **0** | **0** | **0** |
| `bosshit.pkl` | 52 | 443 | 26 | 52 | **0** | **0** | **0** |
| `blowbolt.pkl` | 54 | 494 | 27 | 54 | **0** | **0** | **0** |

[MEASURED]

`$9E85` runs at **0.5 per frame** — a third routine reaching that cadence by a third mechanism (`$9E57`, an SMO frame-edge detector, plus the `$9E5D` cooldown) — and `$9E90` runs twice for each, once per slot, exactly as the old SPEC's "correction to the facet's two CALLs" describes. But `$A314`, `$9F29` and `$9F56` are at **zero in every one of them**, because `$9E94 BIT 7,(IY+7) / RET z` rejects: **no shipped boss capture has a live bolt.** `blowbolt.pkl` holds `$FDEE +7 = $01` — bit 7 clear.

## 17. THE HIT AND THE AWARD — `$9F29`, THE `$9F51` SCF, `$9EE7`, `$9F09`, `$8BC2`, `$80FA`

### `$FFEF := $10` IS A SCORE DIGIT, AND I PROVED IT BY SEEDING EVERY BYTE

`$FFED..$FFF0` is the four-byte BCD **pending-score delta** that `$80FA` adds into `$FFE1 + 4p` and `$8161` then clears. `$FFEF` is **byte 2**, the 10,000s/100,000s pair, so `$10` is **+100,000**.

The I9 gate rule says compare every *seeded* byte, not the ones the machine wrote. Seeding P1's score `$FFE5..$FFE8 := 11 22 33 44`, the delta `$FFED..$FFF0 := 55 66 77 88`, and HIGH `$FFE1..$FFE4 := 99 88 77 66`, then driving `$8E3A` to completion [MEASURED, this pass]:

```
$FFE5 P1_0    11 -> 66   (+55)
$FFE6 P1_1    22 -> 88   (+66)
$FFE7 P1_2    33 -> 43   (+10)   <-- $8E58's byte, and it REPLACED my $77
$FFE8 P1_3    44 -> 32   (+88, BCD carry out)
$FFED..$FFF0  55 66 77 88 -> 00 00 00 00
$FFE1..$FFE4  99 88 77 66 -> unchanged
```

Three things fall out of that table that the drafts do not say:

- **`$8E58` is a STORE, not an add.** My seeded `$77` in `$FFEF` was destroyed. Any 10,000s/100,000s award already pending in the same frame is **lost** when the boss dies. (The drafts' "+100000" is right; "the death pays 100,000" is right; "the death *adds* 100,000 to whatever is pending" would be wrong.)
- **HIGH does not always track.** The constructive pass measured HIGH following the new score; here it did not, because my seeded HIGH (`$99887766`) still exceeded the result (`$32438866`). `$80FA`'s HIGH update is a **comparison**, so "HIGH tracks" is a property of the shipped numbers, not of the routine.
- **The clear at `$8161` is only visible because the seed was non-zero** — TRAPS #44 in its exact form. An unseeded run writes zeros over zeros.

`$FFEF`'s other writer is the 16-bit store `$8F66`/`$8F6F LD ($FFEE),HL` in the treasure-room tail, where `HL = $0100` (10,000) or `DE = $0050` (5,000) [READ from `$8F4C..$8F77`; the award arithmetic is I11's, cited not re-opened]. **Nothing anywhere reads `$FFEF` as a flag.** SPEC.md:3082's "(death signal)" is REFUTED and stays refuted.
