# M7.7 (d)/(e) -- the ITEM and CORPSE->FRUIT chain: the reading pass

Produced 2026-09-16 by a six-reader multi-agent pass over the Z80 bytes plus a synthesis that
re-verified every load-bearing claim itself.  I independently confirmed two of the load-bearing
findings before the readers returned (the four-bit type, and the $F8/$F0 mask split), so those
two are corroborated from two directions.

NOTHING HERE IS GATED YET.  This is the reading, not the measurement.  The increment plan at the
end is how it gets measured.  Treat the LOW CONFIDENCE section as a to-verify list, not as fact.

## The settled model

THE ITEM / CORPSE / SCORE CHAIN — one reconciled model. Everything below was re-verified by me against build/image.bin unless marked otherwise.

=== 1. THE ITEM BLOCK: ONE 64-BYTE ALLOCATION, TWO PASSES ===
$9603..$9642 is ONE 64-byte block of 32 x 2-byte slots, cleared as one unit at round build:
  $8C5E 21 03 96 LD HL,$9603 / 8C61 06 40 LD B,$40 / 8C63 CD 49 AA CALL $AA49  ($AA49 = XOR A/LD (HL),A/INC HL/DJNZ/RET)
  * slot 0  = $9603/$9604 = THE POWER-UP SLOT  (one at a time)
  * slots 1..31 = $9605..$9642 = THE FRUIT / POINTS-ITEM TABLE (31 entries)
ENTRY LAYOUT (settled from all three writers, not guessed):
  byte0 = (X & $F0) | (type & $0F)      type is FOUR bits (0..15); X is always a multiple of 16
  byte1 = (Y & $F8) | (phase & 7)       Y is a multiple of 8; phase 0..7
  byte0 == 0 means EMPTY. byte1 is NOT part of the emptiness test and is NOT cleared on collect.
Writers (all verified):
  $8B9B E6 F0 AND $F0 / 8B9D LD B,A / ... / 8BA6 B0 OR B / 8BA7 77 LD (HL),A   (corpse landing)
  $8A02 7E LD A,(HL) / 8A03 E6 F0 AND $F0 / 8A05 B1 OR C / 8A06 77 LD (HL),A   (both spawns)
  $951B B5 OR L / 951C DD 77 00 LD (IX),A                                      (transition row)

=== 2. THE PER-FRAME PASS ===
$8D4C CD 69 86 CALL $8669  (main-loop chain; $8D46 CALL $A824 and $8D49 CALL $C002 precede it and are DIFFERENT subsystems)
$8669 CD CB 89 CALL $89CB              ; the spawn flow, ALWAYS runs
  866C DD 21 80 FD LD IX,$FD80
  8670 DD CB 5A 66 BIT 4,(IX+$5A) / 8674 20 13 JR nz,$8689   ; P1 water-carry -> BYPASS
  8676 DD CB 64 66 BIT 4,(IX+$64) / 867A 20 0D JR nz,$8689   ; P2 water-carry -> BYPASS
  867C 3A B6 8D LD A,($8DB6) / 867F FE 58 CP $58 / 8681 32 80 86 LD ($8680),A / 8684 C8 RET z
  8685 21 CD 86 LD HL,$86CD / 8688 34 INC (HL)
$8680 IS THE OPERAND of the CP at $867F.  The test is "has $8DB6's low byte CHANGED since the last
call", NOT "== a constant".  LIVE PROOF: $8DB6/$8DB7 = 58 10 and $8680 = 58 in image.bin.
$8DB6/$8DB7 is itself the LD HL,nn operand at $8DB5, self-incremented ($8DB5 21 58 10 / 23 / 22 B6 8D),
called only from $8D81 inside the ISR prologue at $8D72.  So the pass BODY runs once per interrupt
however many times the chain calls $8669 — EXCEPT on the water-carry bypass, where the body runs on
EVERY call and the lifetime counter $86CD does NOT tick.
$8689 (also a direct CALL target from $9531, the round-transition display):
  8689 AF XOR A / 868A 32 2C 87 LD ($872C),A          ; pass flag := 0  (FRUIT pass)
  868D FD 21 03 89 LD IY,$8903                        ; the draw record
  8691 21 05 96 LD HL,$9605 / 8694 06 1F LD B,$1F     ; EXACTLY 31 entries
  8696 7E / 8697 B7 / 8698 C4 A9 86 CALL nz,$86A9 / 869B 23 23 / 869D 10 F7 DJNZ
  869F 21 2C 87 LD HL,$872C / 86A2 34 INC (HL)        ; pass flag := 1  (POWER-UP pass)
  86A3 21 03 96 LD HL,$9603 / 86A6 7E / 86A7 A7 / 86A8 C8 RET z
  86A9 E5 PUSH HL ...                                  ; FALLS THROUGH — $86A8 is a CONDITIONAL RET
$86A9 is both the loop's CALL target and the fall-through target for slot 0.  Verified: the bytes at
$86A6 are 7E A7 C8 E5 C5 — no unconditional RET between $86A8 and $86A9.

=== 3. PER ENTRY ($86B1) ===

  86B4 E5 / 86B5 DD 21 8A FD LD IX,$FD8A / 86B9 CD B2 87 CALL $87B2   ; P2 FIRST

  86CC 3E 93 LD A,n           ; $86CD IS THE OPERAND = the lifetime counter
  86CE E6 FF AND n            ; $86CF IS THE OPERAND = the mask, no writer found -> fixed $FF
  86D0 23 INC HL / 86D1 20 46 JR nz,$8719         ; not a tick -> straight to the draw
  86D3 3A D1 FE LD A,($FED1) / 86D6 B7 / 86D7 20 40 JR nz,$8719   ; heart/level-skip gate
  86D9 7E / 86DA E6 07 / 86DC 3C INC A / 86DD E6 07 / 86DF FE 04 CP 4 / 86E1 20 30 JR nz,$8713
  86E3 2B DEC HL / 86E4 36 00 LD (HL),0     ; EXPIRE, then FALLS THROUGH into the erase $86E6
  8713 4F / 8714 7E / 8715 E6 F8 / 8717 B1 / 8718 77   ; phase written back into byte1 low 3 bits
DELETION FIRES WHEN THE INCREMENTED PHASE == 4, i.e. from phase 3 ONLY.  A phase-4 seed does NOT die
on the next tick (4->5).  Spawn and landing both seed phase 1, so a normal item lives 3 ticks.
Period = 256 counter ticks (mask $FF), and the counter ticks once per gated pass.
$8EDC 32 CD 86 LD ($86CD),$FF at level clear forces the very next tick.
$8EDF/$8EE7 OR 3 into $9604 and $9606 ONLY — forcing phase 3 so the two SPAWNED items self-delete on
that tick.  Corpse fruit in entries 1..30 is NOT touched.

=== 5. THE ERASE ($86E6) ===
Two live entries: EXPIRY (fall-through from $86E4) and COLLECT ($87F4 CD E6 86).
  86E6 3A CE FE / B7 / 86EA C2 14 A3 JP nz,$A314      ; flood -> pixels only, no attribute restore
  86ED..$870F: $AEDC, SUB $A0 into D, four CALL $876C over the same 2x2
  8710 C3 14 A3 JP $A314
  876C 7E LD A,(HL) / 876D E6 20 AND $20 / 876F 3A 09 83 LD A,($8309) / 8772 28 03 JR z,$8777
       8774 3A 0A 83 LD A,($830A) / 8777 12 LD (DE),A / 8778 C9
So the erase reads bit 5 of the COLOUR SHADOW and writes the round's open-cell colour ($8309, live
$46) or platform colour ($830A, live $66) into the REAL attributes.  $A314 then restores the 16x16
pixels from the display shadow (display + $A000) one way only.  For items Y&7 == 0 always, so
$A314's third band ($A348/$A349) always returns immediately — dead code for collectibles.
NOTE: the erase does NOT clear the low-3-bit ink the draw stamped into the shadow… it never wrote
one; $8765 writes the real attrs, so there is nothing to clear.  (This corrects SPEC:1719.)

THE BIT-6 LOCK: an EXHAUSTIVE scan I ran myself finds only two bit-6 operations on struct+0 in the

  811B 1A / 8E ADC A,(HL) / 27 DAA / 77 / 13 / 23 / 8121 10 F8 DJNZ    ; 4-byte BCD add, LSB first

Carry into the first ADC is provably 0 ($8115's sum maxes at $FFE9).  Carry out of the 4th DAA is
discarded — the score wraps mod 100,000,000 with no overflow handling.
HUD ($816B): screen address from the 3-word table $85FC (2B 40 | 1F 40 | 34 40 = $402B HIGH,

=== 8. THE SPAWNS (per round) ===
$8C5E clears the 64-byte block, then $8C66..$8CAD decodes ONE byte b = $FF90[round-1] (81 bytes,
$FF90..$FFE0):
  X_powerup = (b >> 1) & $70                 ; multiple of 16, 0..112
  X_points  = (256 - (X_powerup + 16)) & $FF ; the mirror, 144..240
  Ybyte     = ((((b & $0F) << 4) >> 1) | 1)  with bit 7 ORed in if the round is in the 14-byte list
              $860F (04 05 19 26 29 2B 2C 2E 34 40 48 4B 51 00)
  X_powerup -> $8CAE, X_points -> $8CAF, Ybyte -> BOTH $9604 and $9606, $8CB0 := 0
  round 81 -> RET unchanged; else if the round is ODD, SWAP $8CAE/$8CAF ($8CAA 22 AE 8C LD ($8CAE),HL)
VERIFIED five ways against the live round-80 dump: b=$68 -> X_pu=$30, X_pt=$C0, Ybyte=$41;
image.bin holds $8CAE=$30, $8CAF=$C0, $9606=$41, $9603=$3D (=$30|13), $9604=$43 (=$41|3 from $8EE2).
$89CB (called first thing by $8669 every frame):
  round >= 80 -> JR nc,$8A09; round 80 exactly also does LD (HL),0 (clears both latches); only the
  POWER-UP spawns, no timer gate, and the POINTS ITEM NEVER SPAWNS on rounds 80/81.
  round < 80 -> gated on $8DB7, the HIGH byte of the round timer: == 4 -> power-up ($8A0D),
  == 2 -> points item, else RET.  One-shot latches in $8CB0: bit 1 = points, bit 0 = power-up.
POINTS-ITEM TYPE ($89E4): type = 12 - $9AE9, with $9AE9 == 0 -> 11 and $9AE9 >= 12 -> 0.
$9AE8/$9AE9 is a 16-bit SNAPSHOT of $8DB6 taken at level clear ($8EEF 2A B6 8D / 8EF2 22 E8 9A).
It is NOT a counter: exactly one writer ($8EF3) and one reader ($89E7) in the whole image.  So a
fast previous round gives a high-value item.
POWER-UP TYPE ($8A12..$8A59):
  round == 80 -> 13 forced;  round == 81 -> 12 forced
  round in $8A62 (03 0C 18 1E 20 22 24 29 36 3B 3F 43 45 46 4B 4D) -> the $8A2E draw {3,3,4,5}
  otherwise -> the $8A38 draw: LD A,R / AND $0F, then CPIR C=6 over $8A72 (0D 03 04 05 <patch> 2A);
    FOUND -> XOR A (type 0); NOT FOUND -> keep.  So it is the identity on 0..15 except {3,4,5,13}->0.
  THE UMBRELLA LOCK: $8A76 is the 5th exclusion byte.  $9707 writes $2A (a sentinel no 0..15 draw can
    match) at new game; $8A49 writes 6 the instant a draw produces 6 — so the umbrella spawns AT MOST
    ONCE PER GAME, and the lock arms at SPAWN, not at collect.  MEASURED ACROSS SNAPSHOTS: $8A76 =

  then: CP 6 -> arm the lock; CP 7 and ($7E0E)==2 (a water round) -> ADD A,A -> type 14 (shoes).
BOTH SPAWNS share $89FB: LDI the staged X byte into the destination, then byte0 = (byte0 & $F0) | type.
  $89F5 11 05 96 LD DE,$9605  -> the POINTS ITEM, table ENTRY 0
  $8A5A 11 03 96 LD DE,$9603  -> the POWER-UP slot   ($8A60 18 99 JR $89FB)

=== 9. THE CORPSE -> FRUIT CHAIN ===
A corpse is an ordinary $FD80 entity slot (stride 10) with (+7) bit 3 set ("self-drawn, not a normal
entity") and (+9) == $FF ("I am a corpse").  Dispatch: $AAB6 BIT 7,B / JR z,$AB03 ; $AABA BIT 3,B /
JR nz,$AAFC ; $AAFC LD A,(IY+9) / INC A / CALL z,$8A78.  The renderer $A44D/$A454 sends bit-3 slots
to $A437, which marks them done and draws nothing.
BIRTH $8BC2 (four call sites: $92A2, $93D0, $9EFE, $B82B):
  DEC ($AA5F) ; CALL $8C51 (runs the entity master once with the tail pinned to RET, i.e. the ENEMY's
  final repaint) ; ptr := $C700 ; (+9) := $FF ;
  draw1 = $FE85 -> (A & 7) + 8  -> LOW nibble of (+8) = rise-leg step count, 8..15
  draw2 = $FE85 -> (A & 3) + 1  -> HIGH nibble of (+8) = X speed index, 1..4
  RR H of draw2's H -> bit 0 of (+7) = the X DIRECTION ; (+7) = $8C | thatbit ; (+4) := 0 ;
  (+5) := X & $F8 and (+3) := same ; (+6) := Y & $F8 and (+2) := same.
FLIGHT ($8A78, bit 4 of (+7) CLEAR):
  $8A7D CALL $BF0A — and $BF0A has NO RET: it sets the cache to the CURRENT position and FALLS
  THROUGH into $BF16, so "set the cache" ALSO ERASES.  Every frame begins "erase me where I am".
  $8A80 (LIVE CODE, reached ONLY by fall-through — see contradictions) BIT 4,(IY+7) / JP nz,$8B4E.
  ODD ($FEC6 & 1) frames: JP $A26F, redraw only.  EVEN frames: shimmer cursor (+4) cycles 0,1,2
  selecting $C700/$D340/$D360 ; Y steps +8 (bit1 set, wrap to $00 at $C0) or -8 (bit1 clear, wrap to
  $B8 on borrow) ; then the packed (+8) is serviced: the LOW nibble counts down, and while >= 1 the
  X step is h'*8 where h' = high-1 (or a fresh ($FE85 & 3)+1 when high was 1), signed by bit 0 and
  clamped to [$10,$E0] with $8B45 (XOR 1) flipping the direction at each clamp.
  Leg end, bit1 CLEAR (rising) -> SET 1, fresh ($FE85 & 7)+8, continue.
  Leg end, bit1 SET (descending) -> SET 4 (fall phase), (+4):=0, clamp X, AND $F0, and RET at $8AF7
  WITHOUT drawing — one frame where the corpse is erased and not repainted.
FALL ($8B4E, EVERY frame, not parity-gated): (+4) INC'd as a 256-frame timeout (JR z -> $8B83);
  sprite forced to $C700 every frame; Y += 2 while the floor probe says air.  The probe is SIX cells
  of the colour shadow via $AED1 (which returns the dummy HL=$712F / A=0 for Y+16 < $18):
  land only if (X,Y+16) or (X+8,Y+16) is SOLID (bit 5) AND all four of (X,Y+8),(X+8,Y+8),(X,Y),(X+8,Y)
  are AIR.  If embedded, KEEP DESCENDING.  Polarity: nz == bit5 set == solid, in both $8B69/$8B6E and
  in $8BB4's RET nz.

- READER 4's bit-2 ANOMALY, and the method behind it. Three round-4 dumps (extend/extn/hurry_image) hold five $C700/(+9)=$FF husks with (+7) = $3A/$3B (bit 2 CLEAR) while candy_image and fruit_image hold $3E/$3F, and $8BC2 8BF6 CB D7 SET 2,A can only produce $8C/$8D -> $3E/$3F. Reader 4 declared this unexplained after an 'exhaustive' RES 2 scan. THE SCAN HAD A HOLE: I found 23 whole-byte writers of (IY+7) in the image ($7444, $7F00, $8B4A, $8BFA, $945C, $9A00, $9B59, $9CBD, $9E47, $AC35, $AC51, $AC98, $AF12, $B013, $B056, $B1E5, $B236, $B293, $B4E2, $B9C1, $BDE0, $BF1A, $BF35), several of which mask bits (e.g. $99FA LD A,(IY+7) / A1 AND C / F6 40 OR $40 / 9A00 LD (IY+7),A). The anomaly is real, its cause is NOT settled, and Reader 4's refutation method should not be reused. Bit 2 is never TESTED in the corpse chain, so it is behaviourally inert there -- do not let it block the port, but do not repeat the 'exhaustive scan proves a negative' claim either.

- READER 2's DECODE of the three historical score readings ('+1000' = type 0, '+80000' = type 11, '+40000' = type 10, all read through a window one byte left of P1's base). The arithmetic is elegant and the conclusion is now independently CONFIRMED by the three frozen snapshot pairs, but the step itself is an inference about an observation nobody can re-run. Treat the CONCLUSION (values are 10/800/400 internal) as settled and the STORY (how the misreading arose) as plausible reconstruction.

- READER 2's U3: 'THE HIGH-SCORE ABANDON BRANCH ($8139 JP $8158) IS UNREACHABLE IN 1P -- the high score equals P1 after the first award forever.' THIS IS FALSE. Reader 2 generalised from image.bin, where HIGH and P1 happen to be identical. In crown_image, spawn_image and fruit_image, HIGH = 00020000 (the default 200,000) while P1 is 340/0/320, so the abandon branch runs on EVERY award in those captures. - READER 1's claim that the $9531 row writer's phase-4 seed means 'one tick of the stepper would delete every one of them'. WRONG -- deletion fires only when the INCREMENTED phase equals 4, i.e. from phase 3. Reader 3 has it right. Reader 1's surrounding facts about $9508-$9535 (16 entries rewritten 10 times, not 160 written once) are correct.

- READER 4's claim that 'the fruit you see is the husk's last-drawn $C700 pixels, left on a display that is never repainted'. WRONG -- the item pass draws each non-empty entry every gated frame with sprite $5D00+(type+10)*32 at (byte0 & $F0, byte1 & $F8). Reader 4's separate, stronger claim -- that the landed slot is FREED and inert -- is correct and verified.

- READER 3's statement that $8769 holds $03 in image.bin. It holds $01. Across the thirteen in-game dumps it holds $01, $02, $03, $05 and $06. The CONCLUSION (it is a self-modified per-item ink operand, not the constant 3 of SPEC:1719) is correct and now measured; only the cited live value is wrong.

Reader 3 additionally asserts the handler is the IM2 target because 'C3 72 8D' sits at $FFF4 -- but in build/image.bin that byte triple is at $FFF5, not $FFF4 ($FFF0..$FFF7 = 00 18 78 18 C3 72 8D 10). - THE BIT-6 COLLECT LOCK'S REAL-PLAY CONSEQUENCE. The bytes are certain: only BIT 6 at $87E2/$BDC2 and SET 6,(HL) at $889F/$88A4 exist, with no RES 6 anywhere; the only clears are whole-byte writes ($99D4's AND $80 at respawn, $9290, $AB8B, the new-game zero). - READER 6's LDI/BC RUNAWAY at $C016. The Z80 semantics are not in dispute (LDI decrements the 16-bit BC, so C == 0 costs a B), and C is genuinely live input set at $C023 from the PREVIOUS serviced slot's X & $F8, with the first slot's C inherited from the caller. But whether C == 0 ever coincides with B == 1 in play is unmeasured, and so is what C actually holds on entry from $8D49. Model the LDI's side effect; do not claim the runaway happens.

- READER 5's ROUND-77 CPIR OFF-BY-ONE and the dead 6th slot of $8A72. The reasoning is correct and I verified the tables and the INC C / DEC C test, but neither has been executed. One harness call each settles them.

- READER 4's $AA5F DOUBLE-DECREMENT (that $8BC2's DEC ($AA5F) plus $A437's later decrement for the same slot leaves the sweep one short). Reader 4 labelled it an inference and did not chase the blit's return path. Unmeasured; sweep I in that reader's plan is the right test.

- READER 5's 'POWER-UP UPGRADES PERSIST FOR THE WHOLE GAME because $97D2 has exactly one call reference ($97CC), P2 arriving by fall-through'. The call-reference scan is right and I confirmed the live evidence (image.bin P1 $FDDF = 3 upgraded while $FDDE = 8 default, P2 both default). I could not reproduce it: $A9EA holds 40 20 10 followed immediately by code ($A9ED = 3A 09 86 LD A,($8609)), and $A9BD is a plain LD DE,nn with no indirection. ## The increment plan

### 1. I1 -- the item block, the two-pass scan, and the round clear

**Scope.** The 64-byte block $9603..$9642 as 32 slots x 2 bytes with byte0 = (X&$F0)|(type&$0F), byte1 = (Y&$F8)|(phase&7), byte0==0 == empty. The $8C5E round clear (64 bytes from $9603, via $AA49). The $8689 walk: $872C := 0, 31 entries from $9605 with B=$1F, then $872C := 1 and ONE fall-through pass over $9603 guarded by `AND A / RET z`. No drawing, no collision yet -- just the traversal order and which slots get visited. Model $872C as a BYTE (the bank select tests DEC H for exactly 1; $8781/$8822 test OR A for non-zero).

**Oracle.** tools/itemscan.py. Entry point: CALL $8689 with $87B2 poked to $C9 (collection off) and $86E6's first byte poked to $C9 (erase off) so the pass is pure traversal; record the visit order with a read-watch on $9603..$9644. Also CALL $8C5E with $8609 swept 1..81. Pin SP before EVERY call (Harness.call pushes 6 sentinels and never restores SP -- it drifts 10 bytes per call) and assert the returned sentinel index is 0. Watch $9603..$9644 (66 bytes, INCLUDING the two overrun bytes), $872C, $8CAE/$8CAF/$8CB0, $9604, $9606. Sweep: (a) all 81 rounds through $8C5E, diffing $8CAE/$8CAF/$9604/$9606 against the $FF90 decode; (b) a table seeded with a distinct byte0 in every one of the 32 slots, asserting exactly 32 visits in the order 1..31 then 0. Freeze build/itemscan_fixture.json.

**Unreachable (must BUILD a world).** The $9603 slot is EMPTY in most captured rounds, so the whole second pass never runs -- poke $9603 non-zero. Rounds 80/81's exemptions ($8CA5 CP $51 / RET z, and the odd-round swap) need $8609 poked. The two-byte overrun at $9643/$9644 needs all 30 corpse slots occupied. The $7F1B LDI-chain overlay (32 x `ED A0` + `C9` written over $9603..$9643, run by CALL $9603 from $8421/$843B/$8465/$847D) cannot be reached from a live round -- decide by trace whether those copiers are boot-only; if they are, the port ignores the overlay.

**Equal answers (where a gate could pass testing nothing).** THE ODD-ROUND SWAP is invisible on every even round, and the one live dump is round 80 (even) -- a model that never swaps passes. Break it by sweeping all 81 rounds and asserting odd rows differ from the naive decode, with round 81 as the control (odd but exempt). 31-vs-32 ENTRIES: in a zero-filled test table, scanning 31 or 32 entries from $9605 gives the same answer; seed $9643 = $FF and $9644 = $FF and assert the pass neither reads nor draws them. THE $8C5E CLEAR: clearing 62 bytes from $9605 and 64 from $9603 are identical when $9603/$9604 are already zero -- seed the whole block to $FF before the call.

**Risk.** Low. Pure data traversal. The only trap is treating $9605 as the base.

### 2. I2 -- unpack, sprite, ink, and the draw ($8779 / $8728 / $A2C2+$A2D5)

**Scope.** $8779: itemDrawX = byte0 & $F0 -> $8908, Y = byte1 & $F8 -> $8909, sprite -> $8903/$8904 by the two formulas ($5D00+(type+10)*32 on the fruit pass, $5D00+$8639[type]*32 on the power-up pass). The $8903..$890C 10-byte draw record as REAL addressable state (absolute reads at $8745/$86ED mean a port that relocates it breaks the ink and the erase while the blit keeps working). $8728: type -> ink via ONE 32-byte table at $861D with a +16 offset for the fruit pass, bit 7 -> LD A,R; the ink into the $8769 operand; four attribute cells at $5800+(Y>>3)*32+(X>>3)+{0,1,32,33} with attr = (attr & $38) | ink. The opaque 16x16 unmasked blit via $A2C2/$A2D5 with the $FD00 row table. The $FECE and $FECF skip branches.

**Oracle.** tools/itemdraw.py, extending tools/bubdraw.py's method. (1) CALL $8779 with HL pointing at a two-byte entry in scratch RAM and $872C forced: 544 rows (byte0 0..255 x byte1 fixed, byte1 0..255 x byte0 fixed, each x $872C in {0,1}); assert $8908 == byte0 & $F0, $8909 == byte1 & $F8, $8903/$8904 == the formula. (2) CALL $8728 (reachable by CALL because it ends JP $A2C2 which RETs): 32 rows, type 0..15 x $872C in {0,1}, reading $8769 directly, with all four attribute cells seeded to $FF first and the 16x16 destination seeded once to $FF and once to $00. Pin SP per call; assert $A307 == $A30C == $B6 after every call (an aborted blit leaves them NOPped and every later OR-blit in the game silently becomes opaque). Freeze build/itemdraw_fixture.json.

**Unreachable (must BUILD a world).** The ENTIRE power-up pass ($872C=1, low bank, $8639 remap) -- $9603 is empty in most captures; poke it or call $86B1 directly. The $FF random ink -- only $861D[10], only via $9603 type 10. Fruit types 12..15 (inks 00/00/01/02, sprites $5FC0..$6020 render as garbage past the end of the item bank) -- the normal drop generator only makes 0..7. The $FECE/$FECF skip branches -- poke them. **Unreachable (must BUILD a world).** THE 256-FRAME FALL TIMEOUT -- a fall from the top of the playfield is about 96 frames at 2 px/frame, so the counter never wraps in play; build a world with shadow bit 5 entirely clear and run 256 frames. THE 'EMBEDDED' GUARD -- in play the corpse always arrives from above, so when the row below is solid its own two rows are clear and the guard never fires; poke bit 5 into the corpse's own cells. THE ABOVE-THE-HUD DUMMY -- $AED1 returns HL = $712F / A = 0 only for Y+16 < $18; img[$712F] and img[$7130] are both $00 so it reads as air, but a port that returned 'solid' there would never be caught in a captured round; poke (IY+6) = $02. THE FULL-TABLE OVERRUN -- rounds carry at most a handful of fruit. THE TYPE WRAP 7 -> 0 -- needs at least 8 landings in one round; captures show at most 5 ($8B9F = $04); seed $8B9F high. **Equal answers (where a gate could pass testing nothing).** `AND $F0` ON X at $8B98 is a NO-OP in every normal landing, because $8AF2 already snapped X to a multiple of 16 when the fall phase began -- a model that writes X unmasked passes forever; enter $8B4E with bit 4 PRE-SET and X = $38 (never snapped) and require byte0's high nibble to be $30. `AND $F8` ON Y at $8BAC is a no-op if you only ever land from an 8-aligned Y -- call $8B83 directly with (IY+6) = $A6. `OR 1` on byte1 is invisible if the target entry already has its low bit set -- seed the whole table to $FF before the call, not to 0. `AND 7` on the type is a no-op for counter values 0..6 -- seed $8B9F to $05 so the wrap is inside a 20-row sweep. THE ROUND RESET: if the oracle starts from a snapshot where $8B9F is already $FF, then 'resets at round init' and 'never resets' both produce type 0 first -- seed a mid-cycle value and require the FIRST landing to give value+1. THE FREE-SLOT BASE: with an empty table, 'scan from $9605' and 'scan from $9607' both end up writing a usable entry, and if entry 0 is occupied by the spawn item they even agree on entry 1 -- run with entry 0 explicitly FREE and assert the write goes to $9607 with $9605 still $00. RES 7 AT LANDING: the frame it lands the sprite is already drawn, so 'freed the slot' and 'left it active' look identical for that frame and often many more -- run 30 more frames and check (+5)/(+6) and ($FECA). THE COLOUR-SHADOW PROBE vs A DISPLAY PROBE: if the built world sets bit 5 AND paints the matching pixels, a model that probes the display gives the same answer -- set bit 5 with NO pixels painted, and separately paint pixels with bit 5 CLEAR.

**Risk.** High. The probe polarity inverts easily, and the type generator is three separate self-modified bytes, one of which is an OPCODE.

### 10. I10 (optional, independent) -- the $5CE0 burst-sparkle engine ($C002)

**Scope.** Not part of the item chain, but it was read in this pass and SPEC currently carries three overlapping and partly wrong accounts of it. 14 slots x 2 bytes at $5CE0..$5CFB; byte0 = (X & $F8) | phase, byte1 = RAW Y; FREE means (byte0 & 7) == 0, not byte0 == 0. Phase 0 or 2 -> erase via $A314; 3..7 -> OR-draw $CA80 via $A2D5; phase 0 also frees. Seeded at $B6FC inside the bubble pop with phase 1, cancelled unless $10 <= Y < $AF, slot 13 reused when the table is full. Lifetime exactly 7 passes. $CAA0 and the JR c at $C03B are structurally DEAD.

**Oracle.** tools/sparkle.py. CALL $C002 with the table poked and BC set EXPLICITLY (C is live input to the LDI at $C016). Seed the shadow $E000..$F7FF with a recognisable per-cell pattern, never zero. Sweep: phase 0..7 in slot 0 with the display cell dirtied; all 14 slots live with distinct X/Y; the same run with C = 0 and C = 1 to expose the LDI's BC decrement. Also CALL $B6D8 with a bubble slot for the Y-range reject and the table-full fallback. Freeze build/sparkle_fixture.json.

**Unreachable (must BUILD a world).** $CAA0 AND THE FRAME-1 BRANCH -- structurally impossible (a new phase of 1 requires an old phase of 0, which $C00E skips). Do NOT write a gate that tries to observe $CAA0 drawn; that gate can only ever fail. Assert the NEGATIVE instead: over the full phase sweep, $C05E/$C05F is never $CAA0, plus a direct phase-0-skip test. THE TABLE-FULL FALLBACK -- needs 14 live particles in one 7-pass window. THE Y-RANGE REJECT. $A314's three-band Y-shift -- $C002 masks Y to &$F8 so Y&7 is always 0 through this engine. THE LDI's B DECREMENT -- needs C == 0 at $C016, which no captured world can arrange. $989C's 24-byte clear in isolation -- in play it is always followed by $BF39 -> $BF53's 28-byte clear.

**Equal answers (where a gate could pass testing nothing).** THE IDEMPOTENT OR: phases 3..7 OR the SAME $CA80 into the SAME cells with no erase between, so a model that draws once, three times or five times produces a byte-identical screen -- capture after EVERY single call, not after the burst, and watch the per-pass table byte (the phase counter is the only thing that actually moves). THE PHASE-2 ERASE LOOKS LIKE A NO-OP because the pop already called $BF0A -> $BF16 and restored that area -- dirty the cell at (X&$F8, Y&$F8) with a pattern NOT in the shadow before the call. ERASE-FROM-A-ZERO-SHADOW: 'copy the shadow back' and 'write zeros' agree if the shadow is 00 -- seed it. THE FREE-SLOT TEST: in a freshly cleared table `(byte0 & 7) == 0` and `byte0 == 0` agree everywhere; they diverge only after a particle has expired (byte0 = X&$F8, non-zero, phase 0) -- run a full lifetime first, then pop again and assert the SAME slot index is reused. SLOT ORDER: with one live particle, 'walk all 14' and 'walk only the active one' agree -- use 14 distinct live particles.

**Risk.** Low for the port (cosmetic), but SPEC needs the three accounts merged into one.
